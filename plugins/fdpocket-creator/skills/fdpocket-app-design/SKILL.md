# 依頼から作るものを決める

目的は、依頼者の業務でそのアプリが使えること。依頼の文面をなぞることではない。
AI は作り直しが安いので、**外れても直せることは聞かずに作って見せる**。聞くのは、聞かないと別物になるときと、取り返せないときだけ。

## 1. まず読む

1. `./input/` の依頼・添付（企画書などの文書は `$fdpocket-app-documents` の手順で全部読む）。
2. 前の版があれば `source/design/context.md`（依頼者の文脈と、依頼者が決めたこと）と `schema.zmodel`、`git log`。
3. 公開済みか: `./input/engagement.json` の `published`。`true` なら本物の利用者とデータがいる前提で扱う（`false` ならまだ作り直せる）。

## 2. 聞くか、作って見せるか

| 状況 | 振る舞い |
|---|---|
| **企画書・仕様の資料が渡されている／依頼が十分に具体的** | **聞き返さない**。資料を正として作りきる。資料に無い細部は推奨で決める。資料どおりには作れない点は、作れる代案で作って理由を結果に書く |
| 曖昧すぎて、作っても当て推量になる（何の業務か・誰が使うかが読めない） | **`stage: "questions"` で具体化する**。読み取れる範囲から作れるアプリの候補を 2〜4 個示して選んでもらう。1〜3 問まで。白紙の質問（「何を作りたいですか？」）はしない |
| 作る中身は分かるが、結果を大きく左右する情報が読めない | 聞いてよい。ただし推奨と「おまかせで進める」を添える |
| 公開済み（`published: true`）の Project で、データの単位・関係を作り直す／権限を広げる | **止まって聞く**（`questions`）。影響を件数で示し、推奨を添える |
| 実在の人に届く・お金が動く（通知の送り先・外部への書き込み・課金） | 止まって聞くか、モックで作って設定を本人に委ねる（`setup`） |
| 依頼者しか知らない情報が要る（どのアカウントか・送信元のアドレス） | **聞かずにモックで作る**。結果の `setup` で設定を案内する |
| 2 通りに読めるが、どちらも具体的 | 可能性の高いほうを小さく作って見せ、`assumptions` に別の読み方を出す |
| 細部（画面の配置・文言・並び順・項目） | 決めて作る。結果にも出さない |

**境目**: 聞かずに作ると、依頼者の欲しいものと別物になる可能性が高いなら聞く。外れても手直しで済むなら作って見せる。
一度具体化したら、残りの細部は作って見せる側に戻る（質問を続けない）。同じアプリで質問だけのターンは連続 2 回まで。3 回目は推奨で進める。
依頼者が「おまかせ」と答えたら、その種類の質問は減らす（`design/context.md` の「好み」に書く）。

## 3. 作って見せるとき: 前提を出す（`assumptions`）

推奨で決めたことのうち、**外れると作りが大きく変わるもの**だけを `build-report.json` の `assumptions` に最大 3 つ出す。

```json
"assumptions": [
  { "id": "tenancy", "text": "店舗ごとにデータを分ける前提で作りました",
    "alternatives": [{ "id": "single", "label": "1 店舗だけで使う" }] }
]
```

- 画面は「この前提で作りました」として示し、各前提に「違う」を出す。押されると、その選択が次の依頼として届く。
- 細部（配置・文言・項目）は出さない。出しすぎると読まれない。

## 4. 質問のターン（`stage: "questions"`）

コードは変えない。`build-report.json` を次の形で出す（bundle・dist は出さない）:

```json
{
  "stage": "questions",
  "summary": "予約アプリの作り方を決める前に 2 点確認させてください",
  "questions": [
    {
      "id": "tenancy", "kind": "single",
      "prompt": "この予約は、複数の店舗で別々に使いますか？",
      "why": "店舗ごとにデータを分けるかで、後から変えにくい作りが決まります",
      "options": [
        { "id": "per-store", "label": "店舗ごとに分ける", "recommended": true },
        { "id": "single", "label": "1 店舗だけで使う" }
      ],
      "default": "per-store"
    }
  ]
}
```

- `kind` は `single`（1 つ選ぶ）/ `multi`（複数選ぶ）/ `text`（短い自由記述）。選択肢は 2〜4 個、**推奨に `recommended: true`**、`default` は「おまかせ」のときの値。
- 質問は最大 3 問。**必ず理由（`why`）を書く**。読める情報（コード・`design/`・添付・接続済みのサービス）で答えが出るものは聞かない。
- 利用者の言語で、業務の言葉で書く（ファイル名・内部の用語を出さない）。

## 5. 企画ターン（`stage: "concept"`）

「画面とデータの案を**先に見せたい**」ときだけ。次のどれかに当たる:

- 公開済み（`published: true`）で、既存のデータモデルを作り直す（モデルの削除・関係の付け替え）
- 依頼者が「先に案を見たい」と頼んだ

新規の Project では、ふつう企画ターンにしない（作って見せるほうが速い）。
企画ターンでは `design/brief.md`・`screens.md`・`data-model.md` を書いて commit し（アプリのコードは変えない）、
最終返信で画面一覧とデータの案・決めてほしい点（2〜3 個まで）を短く示す。dist も掲載情報も作らない。
これらの 3 ファイルは**案を見せるための一時のもの**。作るターンでは `design/context.md` に要点だけ残し、3 ファイルは消す（コードと二重管理にしない）。

## 6. 記憶（`design/context.md`）

**コードを読んでも分からないことだけ**を書く。画面一覧・データモデル・API の説明はコードが正なので書かない。

```markdown
# このアプリの文脈
## 業務
- 使う人 / 今のやり方 / 困りごと / 成功の目安 / 制約
## 依頼者が決めたこと
- 2026-11-07 店舗ごとにデータを分ける（前提カードで確認）
## 好み
- 細部はおまかせが多い
```

- ターンの最初に読み、終わりに更新する。上限 6,000 字（超えたら畳む）。
- 「依頼者が決めたこと」は依頼者の答え（前提・質問）から書く。**後のターンで勝手に消さない・書き換えない**（変えるなら質問する）。
- 未確認の仮定は書かない（毎ターンの `assumptions` に出す。確認されたら「決めたこと」に移す）。
- **顧客名・社内の数字など業務の機微を書かない**（コードを公開すると読める）。要点を数行で。企画書の本文を写さない。

## 7. 作る前の必須チェック

- [ ] **一覧は最初からページング**する（増えうるものは全部。並び順は `createdAt` + `id`）
- [ ] **保護する列**（作成者・所属・状態の遷移）は post-update の対で守る（`$fdpocket-app-data-model` §3）
- [ ] **admin の権限は Permission で分ける**。画面の条件分岐を守りの代わりにしない（`$fdpocket-app-admin`）
- [ ] 利用者を消したときに各モデルの行をどうするか（`onDelete`）を決めた
- [ ] 各 App の capability を「使う操作だけ」に絞った（spec §2）
- [ ] 利用者どうしが文字や画像を送り合うなら、見える範囲を Workspace に閉じた
- [ ] スマホ幅・キーボード表示中に主要な操作へ届く（`$fdpocket-app-ui`）
- [ ] 完成の基準（業務の言葉の名前を付けたテスト）を決めた（`$fdpocket-app-testing` §6）
