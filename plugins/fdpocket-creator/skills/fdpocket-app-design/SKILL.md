# 依頼から画面とデータを決める

## 1. 分解する（`design/brief.md`）

依頼を次の 5 つに分けて書く。前の版があれば先に `design/` と `schema.zmodel` を読み、変える部分だけを書き足す。

| 項目 | 書くこと |
|---|---|
| 誰が | 使う人の役割（例: メンバー・管理者・匿名の閲覧者）。役割ごとに「できること」を 1 行 |
| 何のために | 依頼の目的を 1〜2 文 |
| 主な流れ | 利用者が最初に開いてから目的を達するまでの手順（3〜7 手） |
| 作らないもの | 依頼に無い・今回はやらないこと（スコープの境界。頼まれていない機能を足さない） |
| 前提・仮定 | 依頼から読み取れず自分で決めたこと |

## 2. 画面とデータ（`design/screens.md` / `design/data-model.md`）

- **画面**: App（`web` / `admin`）ごとに、ルート（`/tasks`, `/tasks/$id`）・目的・表示するデータ・操作・空と読み込み中とエラーの表示を表にする。
  スマホ幅を先に考える（片手で使う・キーボードが画面の半分を覆う）。
- **データ**: モデル・主な列・関係（User / Workspace への relation）・**誰が読めて誰が書けるか**（ポリシーの言葉で）・一覧の並び順。
  書き方の規約は `$fdpocket-app-data-model`。
- **管理画面が要るか**: 「管理」「運営」「承認」「ユーザーの権限」が依頼にあるとき、または他人のデータを扱う役割があるときだけ（`$fdpocket-app-admin`）。
- **テナント**: 複数のチーム・家族・組織が別々に使うなら Workspace で分ける。1 人で使う道具なら所有者（User）で分ける。

## 3. 企画ターン（`stage: "concept"`）にするか

作る前に利用者と方向を合わせるのは、次の**どれか**に当たるときだけ:

- 新しい Project で、画面が 5 つ以上・役割が 2 つ以上あり、依頼から形が一意に決まらない
- 既存の Project のデータモデルを作り直す（モデルの削除・関係の付け替え）
- 依頼が抽象的で、解釈によってまったく別のアプリになる

企画ターンでは `design/brief.md`・`screens.md`・`data-model.md` を書いて commit し（アプリのコードは変えない）、
最終返信で画面一覧とデータの案・決めてほしい点（2〜3 個まで）を短く示す。dist も掲載情報も作らない。
それ以外は企画ターンにせず、仮定を `brief.md` に書いて作りきる。

## 4. 作る前の必須チェック

- [ ] **一覧は最初からページング**する（増えうるものは全部。並び順は `createdAt` + `id`）
- [ ] **保護する列**（作成者・所属・状態の遷移）は post-update の対で守る（`$fdpocket-app-data-model` §3）
- [ ] **admin の権限は Permission で分ける**。画面の条件分岐を守りの代わりにしない（`$fdpocket-app-admin`）
- [ ] 利用者を消したときに各モデルの行をどうするか（`onDelete`）を決めた
- [ ] 各 App の capability を「使う操作だけ」に絞った（spec §2）
- [ ] 利用者どうしが文字や画像を送り合うなら、見える範囲を Workspace に閉じた
- [ ] スマホ幅・キーボード表示中に主要な操作へ届く（`$fdpocket-app-ui`）

## 5. 工程の順番

brief → データ（ZModel → `kit generate` → `kit db diff`）→ project.yaml → 画面 → 確かめる（`$fdpocket-app-testing`）→ 掲載（`$fdpocket-app-listing`）→ 着地。
データを先に決めると、画面で使う型（`@workspace/sdk`）が先にそろい、作り直しが減る。
