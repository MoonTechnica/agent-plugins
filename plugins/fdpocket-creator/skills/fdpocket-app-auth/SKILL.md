# ミニアプリの認証

1. FDPocket ログインを標準にする。社外の利用者が FDPocket に登録せず継続して本人の履歴を見るなど、専用アカウントが業務に必要なら `project` を選ぶ。独自ドメインの要望だけなら認証を変えない。アカウント不要の操作には匿名利用を検討する。
2. App ごとに誰を入れるかを決める。両方に対応する場合は `providers: [fdpocket, project]`、利用者向け App が専用アカウントだけなら `[project]`。運営画面は必要な認証方式と Permission に絞る。利用者が自己登録を求めている場合は `registration: self` を使う。`registration: closed` を選ぶ場合は、同じ Project に利用できる既存の専用アカウントか、自己登録できる App があることを確認する。初めて専用認証を使い、登録方針が未確定なら、公開前に利用者へ確認する。専用アカウントの招待・管理者による発行は未提供。登録済み利用者への入場許可は業務権限で扱う。
3. ログインへの遷移には `client.auth.signInWithSuperApp()` を使う。直接アクセスの方式選択・登録・確認・回復は Platform が提供する。パスワード、認証トークン、認証メールを生成 App の DB やログへ保存しない。
4. 履歴や Role は Project の `User.id` に結び付け、メールは連絡先として扱う。同じメールの FDPocket アカウントと専用アカウントは独立する。本人の行と管理者の操作は ZModel と Permission で守る。
5. 公開前に、認証方式の既定動作、対象 App の許可と拒否、同じメールでの独立、登録の可否、失効後のアクセス拒否を検証する。ローカルで確かめた範囲と、公開版で確認した範囲を伝える。

専用ログインは Project を一般公開にした Web App の直接アクセスで使う。公開時に Platform が認証 DB を準備する。専用アカウントの機能は SDK のセッションと業務 DB を基準に設計する。`notifications.triggers` は Project 単位で専用ログインと併用できない。既存通知がある場合は対象機能を確認し、維持する案を依頼者と決める。FDPocket 本体の所属や本人課金を必要とする場合も、今使える方式を伝える。
