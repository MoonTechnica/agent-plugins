# 依頼を閉じる（納品物・検品・止まったとき）

設計: `docs/designs/2026-09-14-agent-first-production-loop.md`（§4〜§6、§10〜§11）

**「できました」を自己申告にしない。** 依頼ごとに納品物（`deliverables`）を宣言し、機械の
検査と別の役（reviewer）の採点が `verifications` に残り、`status` が `passed` になって
初めて報告する。ここはその段取り。

## 1. 最初の 2 手（依頼を受けたら毎回）

```
1. start_timeline(...)                       # まだ本編が無ければ
2. declare_deliverable(kind, title, composition_id, criteria)
```

基準（`criteria`）は依頼文から起こす。形式で決まる門番（lint / check / 空枠 / 黒フレーム /
比率 / 尺の窓 / シーンの網羅）は**サーバが足す**ので書かなくてよい。あなたが書くのは:

| kind | いつ | params / text |
|---|---|---|
| `duration` | 尺の指定がある | `{min_s, max_s}`（**指定の 5/6〜10/9 倍の窓**。「3 分」なら 150〜200 秒。ぴったりは通らない。`python3 <SKILL_DIR>/scripts/duration_window.py --minutes 3`） |
| `uses_reference` | 参照素材を添えられた | `{asset_ids}` |
| `intent` | 依頼の狙い（**1〜3 個**） | 文で。「主人公の顔が毎カット判別できる」「夜市の色味で統一」「最初の 3 秒で状況が分かる」 |
| `captions_aligned` | 字幕を入れる | `{tolerance_s}` |
| `loudness` | 配信先の指定がある | `{target_lufs, tolerance}` |

人の追伸（「やっぱり 2 分に」）は `update_deliverable_criteria` で `source='user'` として写す。
人の基準はエージェントの基準に勝つ。決着した納品物の基準は変えられない（新しく宣言する）。
返ってきた `criteria` が採点表なので、**省いた門番が黙って入っている**のを知っておく。

## 2. question は開始前に 1 問だけ

聞くのは次の**どれかのときだけ**。それ以外は聞かずに基準を宣言して進む（決めきれないことは
自分で決め、決めたことを確定行に書く）。**走り出したら聞かない。**

- 形式（anime / mv / footage_edit / explainer …）が依頼文からも既存の設定からも決まらない
- 対象になりうる本編（composition）が 2 本以上あって、どれか指定が無い
- 新規作品で、尺も比率も参照素材も無い

## 3. 検品の流れ（各段で何が残るか）

| 段 | 残るもの | 誰が |
|---|---|---|
| バンドルを置く | L0 lint（error なら書かれない。warning は戻り値） | サーバ |
| 束ねたら | L1 `hyperframes check` → `record_check`（現在の `head_seq`） | compositor |
| 書き出し | L2 媒体 QC（黒・凍結・無音・音量・尺・字幕）→ L3 意図（Gemini） | プラットフォーム |
| 書き出しが終わったら | `open_work(role='reviewer', target_kind='deliverable', target_id)` | director |
| reviewer の判定 | `verifications(reviewer)`。`ok` なら `passed`、違えば `failed`（round +1） | reviewer |
| `passed` | `report_deliverable(deliverable_id, summary)` → 完了カード（Slack にも出る） | director |

`failed` で round が残っていれば、落ちた基準の**層を直して**（本文なら compositor に
`patch` させ、動画ならだめな区間を `video_edit` で直して差し替え）検品をやり直す。
シーン全体の撮り直しは人の指示が要る（`cinematographer` §5）。
**reviewer の判定を自分で上書きしない。** 判定に納得できなくても、直すのは対象のほう。

### 映像の検品が切ってあるとき（既定）

プロジェクト設定 `agent_policy.media_review` が `false`（**既定**）のときは、

- L3（Gemini の意図判定）は**走らない**（`verifications` に L3 の行が増えない）
- `intent` や `no_black` のように**直すのに再生成が要る基準は `warn` で保存される**

したがって `failed` になるのは**テキストと構造**（脚本・字幕・lint・check・尺・比率・
網羅）が落ちたときだけで、そこを直すのに撮り直しは要らない。**`warn` の所見を理由に
シーンを撮り直さない。** 絵として作り直すかどうかは、完了カードを見た人が決める
（`request_change` / `revert` / `waive`）。直せと言われていないのに撮り直すと、
依頼の予算をそこで使い切る。

## 4. 止まったとき（次の一手を書かずに終えない）

| 止まり方 | どう分かるか |
|---|---|
| round の上限 | `open_work(reviewer)` が `max_review_rounds` で断る |
| 依頼の予算超過 | `generate_scene` / `generate_asset` / `render_composition` が予算切れで断られる。セッションも止まる |
| カットの差し替えで直らない | 同じカットを 2 回編集しても直らない / 声・人物の位置の問題 / 分けて直したカットの継ぎ目が二重に見える（`cinematographer` の references/partial-edit.md §6）。撮り直すかは人が決める |
| 承認待ち | tool が承認待ちの id を返す。`render_composition` は投げずに `status='blocked'` + `approval_id` を返す（プロジェクトが書き出しを毎回確認する設定か、見積が依頼の予算の残りに入らないとき）。予算の引き上げも同じ承認待ち。**人が承認すればプラットフォームが実行する**（自分で投げ直さない。結果は会話の system 行に残り、次の発話で `get_deliverable` で追いつく） |

どれも確定行に **3 点**を書いてターンを終える:

1. **合格しなかった基準**（または止めた理由）
2. **試したこと**（何を何回、どう変えたか）
3. **人に決めてほしいこと** —— waive するか / 基準を変えるか / 予算を上げるか / 縮小案で行くか

上限で止まった納品物は `report_deliverable` で完了カードにする（人が waive を押せる）。
黙ってリトライを続けない。黙って終わらない。

### 検品・解析の外部サービスが使えないとき（Gemini の 402 など）は、止まらずに続ける

**Gemini が使えない（残高不足の 402・429・タイムアウト・一時的な障害）ことは、作業全体を止める理由にならない。**
2026-11-17 に、検品の Gemini が 402 で失敗しただけで「新たな動画生成は止めています」と全部止まった。

| 失敗の種類 | どうする |
|---|---|
| **Gemini / 外部の解析・検品**が失敗（402・429・タイムアウト・障害） | **その確認だけを飛ばす**。同じ呼び出しを黙って繰り返さない（最大 1 回だけ再試行）。確認できなかった項目は完了カードに「未確認」と書く |
| 生成・編集・配置・束ね・書き出しなど、**Gemini に依存しない作業** | **そのまま続ける**。検品の失敗を理由に `generate_*` を止めない |
| 次の工程が Gemini の結果を**入力として要る**（曲の地図 → 分割の決定など） | その工程だけ保留。**ほかの独立した工程を先に進める**。保留したものは最後に「人に決めてほしいこと」へ書く |
| **組織の残高不足・依頼の予算超過**（`InsufficientCreditsError`、`generate_*` / `render_composition` が断る） | **これは止まる**（生成そのものにお金が要る）。§4 の止まり方として 3 点を書く |

- 見分け方: **自社の課金（残高・予算）の断り**（文に「残高」「予算」が出る）は止まる。**外部サービスの失敗**（文に Gemini・402・429・quota・timeout が出る）は止まらない。迷ったら、同じ工程を 1 回だけ再試行して、同じ失敗なら飛ばす
- 飛ばしたことは**最後にまとめて 1 回**報告する: 「何を確認できなかったか / どの工程は続けたか / 人がやること（残高の補充など）」
- 確認できていないものを「確認済み」と書かない。ただし作業は止めず、**人が後から確かめられる形**（完了カード・未確認の一覧）で渡す

## 5. 走っている間の追伸・やり直し・戻す

設計 §9 / §10.2。

**追伸。** あなたが作業している間に人が送った発話は捨てられず、ターンの終わりに
次の発話として届く（`<postscript>` で包まれ、古い順に番号が付く）。届いたら、
それまでの作業を捨てずに方向だけ足す。基準が変わる内容（「やっぱり 2 分に」）は
`update_deliverable_criteria` に写す。

**やり直し。** 人が「やり直す」を押すと、プラットフォームがそのターンの変更を戻してから、
同じ依頼を `<retry>`（前回が止まった理由つき）を添えて送り直す。前回と同じ手順を
なぞらず、止まった理由を避ける段取りにする。

**戻す。** 「この依頼をなかったことに」「さっきの変更を戻して」と頼まれたら:

| 頼まれ方 | 呼ぶもの |
|---|---|
| 直前の 1 ターンぶん | `revert_turn(turn_id)` |
| 依頼（このスレッド）の全部 | `revert_thread(thread_id)` |

戻るのは本編の変更（後から人が触ったクリップは残る）・依頼が作った素材（除外）・
レーンの依頼のシーン（破棄）・納品物（cancelled）。人が確定した素材・シーンと、
人が受け入れた納品物は残る。戻り値の `conflicts` と `moved`（人が編集し続けていて
戻せなかった本編）は確定行で人に伝える。戻した結果は会話にも残るので、同じ内容を
長く書き直さない。
