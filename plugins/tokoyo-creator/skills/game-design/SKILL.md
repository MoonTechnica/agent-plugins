遊べる核ができたら `$game-playtest` の `references/development-preview.md` を読み、通常開始ケースと本編factoryを使う代表試験場を用意する。メニューUIは作品に合わせてゲームリポジトリ内の`debug/`へ作り、SDKの型付き操作でHostの認可・専用Scopeに接続する。本番成果物へ含めない。Document read/write要求は今回の対象外。

# ゲームの作り方（工程と企画）

プロのゲーム開発の順序で作る: **核を決める → 絵で合意する → 素材を設計する → 醜いまま遊べる形にする →
遊んで直す → 数値で整える → 磨く → 掲載する**。順序を飛ばすと、見た目は整っているのに遊べないゲームになる。

## 1. 工程と完了条件

`update_plan` の計画は、このターンで通る段階から起こす（項目の書き方は `instructions.md` §0「進め方」）。

| # | 段階 | 次へ行ける条件 | 使う Skill |
|---|---|---|---|
| 1 | 企画 | `design/brief.md` の全見出しが埋まり、ジャンルの下限（[references/genres-minimum.md](references/genres-minimum.md)）が列挙されている。核の動詞・看板の仕掛け・テーマの規則・山と休みを [references/fun.md](references/fun.md) §1 で決め、該当ジャンルの [references/exemplars.md](references/exemplars.md) を読んだ | この Skill §2 |
| 2 | 絵で合意 | コンセプト画像（`key-art` / `hero`）とスタイルガイドがある。**新しいゲームの最初のターンと、見た目・遊びの核を変えるときは方向を見せて止まる**（hosted は企画のターンとして終え、手元は会話で見せる。利用者が「確認なしで」「おまかせで」と言ったときは見せずに作り進める。条件は `$game-art-direction` §2） | `$game-art-direction` |
| 3 | 素材の設計 | `design/asset-manifest.md` の全行に経路・理由・枠があり、合計が予算内 | `$game-art-direction` |
| 4 | 核を遊べる形に | 開始 → 核の行為 → 結果/進行 → 次の区切りが回る。進行型は保存 → 再開も核として検査する（`rules.gd` の無い前の版を続けるときは下の「2 回目以降」） | この Skill §3、`$game-playtest` |
| 5 | 素材の差し替え | manifest の全行が済み、`design/game-assets.json`の名前と実装参照が一致する（コードで作るモデル/音も含む） | `$game-asset-tools` |
| 6 | 遊んで直す | 確認済みと未確認が明確。確認できた重大な失敗は修正済み。新規制作と核の変更では [references/fun.md](references/fun.md) §4 の点検表を当て、効くものから直した。公開前検証/作者プレビュー待ちへ ✓ を付けない | `$game-playtest` |
| 7 | 数値で整える | 導入は安全で、区切りの長さと難易度がbriefに合う。全作品に短時間終了を課さない | この Skill §3 |
| 8 | 磨く | §4 のチェックが埋まる。**この段階で機能を足さない** | `$game-ux` |
| 9 | 掲載 | `$game-listing` のチェック | `$game-listing` |

- **2 回目以降のターン**は、依頼が変える段階から始める。`design/` の文書は変わったところだけ直す。
  - 素材の編集は`$game-asset-tools`の`asset-context`で対象IDと参照先を絞り、
    承認済み基準・原型・レシピを再利用する。必要な差分と影響する派生だけ更新し、全素材を検索/生成し直さない。
  - 数値・見た目の細部・不具合 → 4〜9 のうち要るところ
  - 遊びの核（ルール・操作・目的）が変わる → 1 から
  - 見た目の方向が変わる（絵柄・主役・世界観）→ 2 から
- 前の版に `design/` が無い（この工程より前に作られた）ときは、今の中身から `brief.md` と `style-guide.md` を起こしてから続ける。
  ただし**外部参加のfeat（`./input/branch.json`。手元では `get_app` の `branch` の `requires_proposal` が `true`）では起こさない**（本流への提案に関係の無い差分を増やさない）。
- 前の版に `godot/rules.gd` が無いときは、**依頼の変更のために作り直さない**（`instructions.md` §4.0 の「変更だけ」が優先）。
  ルール検査（`$game-playtest` §2）はその版では省き、`notes` に「rules.gd が無いのでルール検査を省いた」と 1 行書く。
  `rules.gd` / `tuning.gd` に分けるのは、遊びの核から作り直すとき（段階 1 から）だけ。派生では分けない。
- 自己試遊の結果（`./input/playtest-report.json`）があれば、段階 6 の前に読んで直す（`$game-playtest`）。
- **ベストプラクティスに沿って実装し、その上で追加最適化する。** 新規制作/変更部分の実装前に
  [references/performance-risk.md](references/performance-risk.md) §0と使用エンジンの指針を読み、該当する基本対策を適用する。
  実描画で改善すべき箇所を見つけ、原因に合う局所変更を同条件で比較し、画質/操作感/ルールも再確認する。
  設計時と重い表現を足す前には同参照に従い、
  懸念を先に伝え、利用できる描画環境で小さく試作して負荷を比較する。完成後だけの確認にしない。
  警告で承認待ちにせず、軽量案で制作を続ける。実測できなかった環境は未確認と明記する。
- **ステージ/マップ/配置は `$game-level-design`。** 段階1で体験と制約を決め、段階3〜4で
  進行と空間を分けて小さな候補を検査・選定する。段階5で採用案を素材化し、段階6〜7で
  影響する経路・進行・実画面を再確認する。企画の合意は既存の段階2だけで、別の承認待ちを足さない。

## 2. 企画（`design/brief.md`）

見出しはこの順で固定。短く、具体的に書く（「楽しい」「爽快」だけで終えない）。

```markdown
# <仮のゲーム名>
## 一文で
上から落ちてくる星を、ジャンプだけで 30 秒間集め続ける。
## 動詞
跳ぶ（1 つだけ。「と」でつながない）
## 狙う感じ
挑戦（Challenge）+ 爽快感（Sensation）
## 看板の仕掛け
星を取るたびに自分が少し重くなり、跳べる高さが下がる（取りすぎると針に近づく）
## テーマの規則
星は流れ星なので斜めに落ちる / 夜が深まるほど暗くなり、光る星しか見えない
## 勝ち・負け・終わり
30 秒で終わる。点数を競う。地面の針に触れたら即終了。
## 1 回の長さ
30〜60 秒
## 進み方
10 秒の波を 3 つ。波ごとに新しい星（分裂する / 逃げる）を足し、波の間に 3 秒の休み。
## 作らないもの
ステージ選択・ショップ・ストーリー・オンライン対戦
## ジャンルと下限
ワンボタン / エンドレス: 加速する難しさ・ベストの記録・ニアミス報酬・1 秒以内の再開
## 道具
Godot 2D（動く物が少ない）
```

| 見出し | 決め方 |
|---|---|
| 動詞 | 遊ぶ人が何度も繰り返す操作を 1 つ。依頼に複数あれば、いちばん触る回数が多いものを核にし、残りは補助にする |
| 狙う感じ | 挑戦 / 爽快感 / 見立て（Fantasy）/ 物語 / 仲間 / 発見 / 表現 / 暇つぶし（Submission）から 1〜2 個。手応えと絵の選択がこれに揃う |
| 看板の仕掛け | このゲームでしかできないこと 1 つ（[references/fun.md](references/fun.md) §1）。ジャンルの下限は看板にならない |
| テーマの規則 | テーマを動詞と規則に変えたもの 2 つ以上。絵を替えても同じなら書き直す |
| 勝ち・負け・終わり | 必ず決める。終わりの無い遊び（育成・放置）でも「1 回の区切り」を決める |
| 1 回の長さ | 操作/戦闘/クエストの区切り、1回のプレイ、作品全体を区別する。短時間ゲームは30秒〜3分が目安、協力卓は現行上限内 |
| 進み方 | 直線で難しくしない。区切り（波・面）ごとの新しい要素と、山の後の休み（[references/fun.md](references/fun.md) §1「山と休み」「起承転結」） |
| 作らないもの | 依頼に無く、核の完成に要らないもの。**ここに書いたものは作らない** |
| ジャンルと下限 | [references/genres-minimum.md](references/genres-minimum.md) の該当行を写す。**下限は依頼に無くても作る**。下限を超える機能は依頼にあるときだけ |
| 道具 | `instructions.md` §4.2 の選び方 |

利用者の依頼に書かれたことは brief より優先する。依頼と下限が食い違ったら依頼に従い、`notes` に 1 行書く。

## 3. ルールと調整値を分ける

```text
godot/
├── tuning.gd   # 調整値だけ（速度・重力・間隔・体力・得点・判定の猶予）。const だけ
├── rules.gd    # 遊びのルールだけ（状態・入力・時間 → 次の状態）。ノード・描画・音・TokoyoApp に触れない
└── main.gd     # 入力を集め、rules を進め、描く・鳴らす（シーンのスクリプト）
```

- `tuning.gd` は `const` だけ（`const FALL_SPEED := 120.0`）。数値をコードに散らさない。
- `rules.gd` は static 関数で書く: `init(seed) -> Dictionary` / `step(state, input, dt) -> Dictionary` / `is_over(state)` / `score(state)` の形。
  乱数は state に持たせた seed から `RandomNumberGenerator` で引く（`randf()` を直接使わない）。これで headless の Godot から
  ルールだけを回せる（`$game-playtest` §2）。物理（`CharacterBody2D` 等）で動く部分は rules に入れず、勝敗・得点・進行の判定だけを置く。
  RPGで不要なscore/ゲーム全体のisOverを強制しない。定義データとruntime進行を分け、局所更新を検査可能にする。
  毎frameの全世界deep cloneは行わず、保存時の固定snapshotとsimulationを分離する。
- RPG/長期探索は [references/rpg.md](references/rpg.md) を先に読む。会話・クエスト・所持品は依頼の核に必要なものだけ作る。
- 対戦は手番・勝敗の判定・1 tick の計算を `server/main.ts` の `defineSpace` だけが持つ（サーバーが権威。`$game-multiplayer` §2）。
  画面側の GDScript は手を送って同期された状態を描くだけで、勝敗を計算しない。
- **プレイヤーに有利に「ごまかす」**のは既定で入れる（`tuning.gd` に値を置く）:
  足場の端から離れても少しの間は跳べる（coyote 80〜120ms）、着地の少し前の入力を覚える（buffer 100ms）、
  当たり判定は見た目より少し小さく、取る判定は少し大きく。

## 4. 磨く（段階 8）

機能は足さず、`$game-ux` §9 のチェック（手応え・読める文字・動きの安全・リザルト・設定）を通し、足りないものだけ入れる。
量と上限は `$game-ux` の references/feedback.md。ここで見るのはそれ以外の 2 つだけ:

- [ ] 勝ち・負けの瞬間に演出があり、何が起きたか分かる
- [ ] BGM と効果音が `design/asset-manifest.md` のとおりにある
- [ ] 新規制作と核の変更: [references/fun.md](references/fun.md) §4 の点検表で残した項目を `design/playtest.md` に書いた

出荷前の最終確認は [references/ship-checklist.md](references/ship-checklist.md)。

## 5. 利用者への返事

最後の返事に次を短く書く（長い説明や自己評価はいらない）:

1. 何を作った / 変えたか（1〜2 行）
2. 確かめたこと（`design/playtest.md` の結果から 2〜3 行。「ビルドが通った」ではなく遊びの振る舞いで）
3. 作らなかったもの・できなかったこと（あれば 1 行）
4. 性能の懸念があれば、推定/実測・測定環境・軽量化・未確認の端末を短く書く。
