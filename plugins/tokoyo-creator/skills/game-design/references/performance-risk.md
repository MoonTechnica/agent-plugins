# ベストプラクティスから始める性能設計と追加最適化

新規制作では設計/実装の前に読む。既存ゲームへの変更では変更部分と影響する場面へ適用する。
**まずベストプラクティスに沿って実装する。その上で実描画を確認し、さらに改善すべき箇所へ追加最適化を試みる。**
基本対策を性能問題が出るまで後回しにしない。作品の画風・操作感・ゲーム性を保ち、低画質を全作品の目的にしない。
警告は情報提供であり、承認待ちや制作停止を追加しない。

## 0. 実装の出発点

固定Godot版の公式マニュアル/API定義と`$game-godot`、`$game-3d-and-bundles`を先に読む。
公式資料の最新APIを同梱版へ無確認で写さず、別版や別エンジンの方式を混ぜない。
ジャンル名ではなく、今回使う機能に次の原則を適用する。対象外の機能を追加する必要はない。

| 領域 | 最初から適用する原則 |
|---|---|
| 解像度/マルチデバイス | 論理座標・CSS表示サイズ・内部描画画素数を分け、DPRを無制限に反映しない。縦横/回転/表示サイズ変更でもHUD・入力座標・ルールを保つ。API対応・入力方式・端末性能を別判定にする |
| 粒子/透明演出 | 発生頻度・寿命・同時数・emitter数を有限にする。個数だけでなく画面占有/重なりを抑え、遠方の装飾は間引く。非表示にしただけで更新停止と扱わない |
| 世界/活動範囲 | 現在必要な地域と近傍を読み、保持/描画/physics/AI/骨格の範囲を分ける。全世界の全件走査・毎frame経路探索を避け、空間検索と時間分散を使う |
| 素材/描画 | 実表示サイズ・同時数に合う形状/texture/材質/骨格を選ぶ。反復素材を共有し、3Dは必要なLODと単純な衝突形状、2Dはatlasと描画状態のまとまりを検討する |
| 光/影/効果 | 静的な光の焼き込みを候補にし、動的shadowの光源/対象/距離/解像度とRTT/全画面pass数を限定する。作品に必要な明暗と手掛かりを保つ |
| 更新/寿命 | UIは変化時に更新。大量の短命objectは有限poolを候補にし、再利用時のbody/animation/timerもreset。共有/専用資源の所有と解放、不要jobの取消を設計する |

資源の所有・解放、処理量の上限、不要更新の回避は基本対策。LOD/atlas/pool/焼き込みは用途に応じて選び、
GPU particles/GPU layer/動的解像度/積極的freeze/追加passは対応と適用条件を確認し、同条件で比較して採用する。
全objectの最大数まで事前確保、全meshのmerge、全FX禁止を一律の最適化にしない。
画質段階を用意する場合は内部解像度・影・装飾・粒子・LODを調整し、入力座標/移動速度/衝突/ルールを変えない。
タッチの有無や端末の種類だけで品質段階を決めず、Web/native共通のCompatibility renderer（WebGL2相当）で遊びと必要な視認性を保つ。

該当原則・選んだ方式・例外と理由を`design/performance.md`へ短く残す。詳細な新規設計書を毎回要求しない。
基本実装の実描画を確認し、予算超過/停止/資源増加など改善すべき箇所があれば原因を分けて追加最適化する。
仮説→局所変更→同条件の前後比較→実画像/操作の確認を行い、効果が無い変更は採用しない。
CPU負荷へ解像度だけを下げるなど原因と異なる対策を繰り返さない。測定できない場合は§3へ進む。

## 1. 設計で気づく

`design/brief.md` に「性能上の懸念」を追記する。懸念が無ければ一行でよい。
名前やジャンルではなく方式・同時量・解像度・更新頻度を確認する。

| 候補 | 重くなりやすい方式 | 最初に試す代案 |
|---|---|---|
| 雲・霧・水面 | 全画面のray marching、多段noise、何重もの透明描画 | 画像、少数の板、低解像度の演出 |
| 光・影・フィルター | 多数の動的shadow、高解像度の描画先、全画面の複数pass | 影を焼く、光源/影/効果を限定する |
| 粒子・草・群衆 | 大量の重なる半透明、個別material/描画、画面外もanimation | 上限、共有/instance、活動範囲を限定 |
| 広い世界・NPC | 全世界更新、全組合せ衝突、全NPCの毎frame経路探索、一括生成 | 地域分割、近傍だけ更新、時間分散 |
| 長時間プレイ | 地域往復ごとにtexture/body/listener等が増え続ける | 所有と解放、保持上限、再訪時の資源数を測る |

雲が画像一枚ならray marchingの警告を出さない。draw callの少なさだけで安全と判断しない。
画素数×覆う割合×反復×pass数は比較の目安であり、GPU時間やFPSへの換算ではない。

懸念を見つけた時点で、利用者へ「方式・理由・代案・まだ推定」を短く伝える。
例: 「雲を画面全体で何十回も計算する方式はスマホで重くなる可能性があります。まず雲だけを描画して、画像で表現する案と比較します。現時点では推定です。」

## 2. 本実装の前に描画して比較する

**懸念がある場合、利用できるブラウザ/作者プレビューで最小試作を実際に動かす。**
ビルド、ルール検査、静止画だけを負荷確認としない。
ゲームの核と懸念の表現を同時に描く小さい試作を作り、以下を行う。

1. 同じカメラ・入力・seed・同時数・内部描画解像度で、演出なし/あり/軽量案を切り替えられるようにする。
   比較用スイッチは制作時だけ。依頼にない製品設定画面を増やさない。
2. 起動/初回shader compilation/地域読込と定常描画を分ける。数秒warm-up後、各条件を30–60秒程度測る。
   条件の順を替えて2–3回比較する。描画後の画面も確認し、演出やゲームが実際に動いていることを確かめる。
3. Godotの`_process`へ一時的な計測Nodeを入れ、毎frame`Time.get_ticks_usec()`の差（実frame間隔）を有限の配列に記録する。
   平滑化/制限後のdeltaやsimulationのdtは計測値に使わない。60秒程度の比較は各条件で配列を新しくし（上限10000件）、
   count/p50/p95/p99/maxを`TokoyoApp.report()`で記録する。
   pause/非表示区間は除外して時計をresetする。サンプルが足りない条件は測定不足とする。
4. Godotの固定版APIで、取得できる描画回数・活動object・texture/body等を併記する。
   CPU側処理時間、frame間隔、GPU時間、素材メモリ推定は別々に書く。
   GPU timerが利用できなければ「未測定」。CPUのrender呼び出し時間をGPU時間と呼ばない。
5. 同じ場面で目標FPSのframe予算を継続的に超える、演出ありだけで停止が増える、資源数が往復ごとに増える場合は
   利用者へ実測結果と簡素化案を伝え、軽量案で再測定する。初期目標は60fps（約16.7ms）、
   依頼/ゲーム性に合う30fps（約33.3ms）も可。refresh rateや計測の揺れを考慮し、単発の閾値超過だけで断定しない。

`design/performance.md` に版/commit・試作か完成版か・端末/OS/ブラウザ/WebView・headlessか・描画backend・
GPU/ソフトウェア描画の確認状況・viewport/DPR/内部描画サイズ・条件・測定時間/サンプル数・数値・変更・未確認を残す。
最適化後の完成場面も測り直す。試作だけの結果を完成版の合格に転記しない。

**PCのスマホ幅、UA変更、CPU throttlingはスマホGPU/WebViewの再現ではない。**
PC/headless/software rendererでの測定は比較/退行検出として扱い、「ほとんどのスマホで快適」と結論しない。
実機へアクセスできる時は、代表的な低〜中性能のiPhone/Androidのアプリ内WebViewでも同じ場面を測る。
長時間の発熱/メモリ検証は`$game-playtest` §5。短い試作ではその合格を主張しない。

## 3. 測れない場合と警告の伝達

ブラウザ/実機/必要な計測APIが無い時は、理由と未確認範囲を記録し、軽い方式を既定にして制作を続ける。
架空のFPSや「実機で確認済み」を書かない。外部端末サービスの契約やPlatformの毎版動的検証を勝手に追加しない。
利用者が明示した重い表現を削る時は、依頼との違いと代案を説明する。

- 手元の制作: 懸念を見つけた時と測定後に制作チャットで伝える。
- hosted制作: 途中のassistantメッセージで推定/実測・理由・代案・未確認環境を伝え、制作を続ける。
  既存の`update_plan`で「雲の負荷を確認」等も示す。`plan.explanation`だけを警告の伝達先にしない
  （現行画面は計画の項目を表示する）。最終返信にも残る懸念と測定結果を書く。
  ツールが無い/失敗した場合は計画を更新できたと主張しない。
- `build-report.json`の`notes`にも残る懸念・測定環境・未確認を記録する。
  詳細記録はソース内の`design/performance.md`。新しい成果物/APIフィールドを作らない。

測定の解釈: Godotの`_process`の間隔と[`Performance`](https://docs.godotengine.org/en/4.5/classes/class_performance.html)のmonitor（`TIME_PROCESS`・draw call・static memory）は
CPU側の値で、GPU実行時間ではない。測った値は`TokoyoApp.report()`で記録する。固定版Godotの公式API定義を正本にする。
