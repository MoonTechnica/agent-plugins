# 素材制作の再利用と局所変更

## 対象だけを調べる（新規・継続編集）

共有SDKのCLIを使う。ゲームのソースディレクトリを渡し、ソースを書き換えずJSONを得る。

```bash
node <kit>/sdk/app-sdk/build-config/kit.mjs asset-context ./source
node <kit>/sdk/app-sdk/build-config/kit.mjs asset-context ./source player-plane
```

- IDなしは名前・種類・用途だけの50件。`next_offset`があれば`--offset <値>`をソースの直後へ置く。
  対象が見つかった時点で止め、毎ターン全ページを取得しない。
- IDあり（最大8件）は対象の実装パス・symbol・素材ID・制作資料の参照を返す。
  `shared_source_candidates`は同じソースファイルを使う対象であり、依存・派生・互換性の確定情報ではない。
  同じファイルにある別キャラを一緒に作り直さない。選択されたsourcesから実際の参照を確認する。
- 一覧がない旧ゲームは`catalog_missing`。選択された対象の既存制作記録・コードを局所的に読む。
  不明なIDを名前で別対象へ置き換えず、現在の認可済みソースで確認する。
- この道具は現在のcheckoutだけを見る。未許可のmain・別feat・他作品の素材を検索しない。

## 基準画像・原型・必要な差分を固定する

1. 現行の`design/style-guide.md`と承認済みの制作資料から、画風の基準とキャラの基準を別々に選ぶ。
   基準画像の実在パス/素材IDを`design/asset-manifest.md`の対象行へ短く記録する。
   同じ説明文を繰り返すだけで同一キャラになると扱わない。
2. 現行の原型・装備・骨格・動作を確認し、変更対象と維持する部分を決める。
   色/寸法/配置だけならコード・既存制作スクリプトのパラメータを変える。
   顔・衣装・シルエットの固有性が必要なものを単なる色替えにしない。
3. 編集機能が使える画像は元画像を入力する。`edit_image`には実際のツールスキーマが許す入力だけを渡す。
   内蔵生成の編集も参照画像を添える。複数参照・マスク・画風学習の機能があると推測しない。
   未対応なら基準を見て具体的に指示し、維持すべき特徴を結果で照合する。
4. 形・リグ・モーション・撮影を分ける。装備の変更で無関係な身体や既存モーションを再生成しない。
   必要な派生だけ更新し、原型のIDと変更後の実装参照を保つ。

## 検証済みの手順をレシピとして使う

すでにある`art/`のスクリプトと完成素材を先に使う。パックを選ぶときは画風に加え、連番・原点・縮尺・骨格・必要クリップがそろうか確認する。
一括取り込みMCPは存在しないので捏造せず、採用したIDを既存の`import_stock_asset`で取り込む。
検索と採否はパック単位でまとめ、同じキャラの連番ごとに検索し直さない。

繰り返すローカルの決定的な加工は共有CLIの`asset-recipe <source-dir> <recipe.json>`で実行できる。
レシピは`art/recipes/`へ置いてcommitする。例:

```json
{
  "version": 1,
  "engine": "node",
  "script": "art/recipes/prop-icons.mjs",
  "inputs": [],
  "outputs": ["coin.svg", "gem.svg"],
  "params": {"size": 128, "items": [
    {"name": "coin", "shape": "coin", "color": "#E8AD30"},
    {"name": "gem", "shape": "gem", "color": "#4DAFCB"}
  ]}
}
```

同梱`<kit>/skills/game-asset-tools/assets/prop-icons.mjs`を`art/recipes/`へコピーすると、このレシピで
coin/gem/potionの小物アイコンをまとめて作れる。適合する画風・用途でだけ使い、主役の代用品にしない。

```bash
node <kit>/sdk/app-sdk/build-config/kit.mjs asset-recipe ./source art/recipes/props.json
```
手元にBlenderがあれば`engine: "blender"`で保存済みの`.py`を実行できる。無ければ既存の素材ツール経路を使う。

- スクリプトには`OUT`（書き出し先）、`INPUTS`（ソースroot）、`ASSET_PARAMS`（JSON）が渡る。
  すべての出力はOUT配下へ書く。入力・importする補助スクリプト・設定・フォントなどは`inputs`へ列挙する。
  外部ファイル・ネットワーク・現在時刻・未固定乱数・未記録の依存に頼る処理や有料生成には使わない。
  外部実行ファイルを使うNodeレシピはそのバージョンもparamsへ明記する。
- スクリプト/入力のSHA256・設定・実行エンジンの版が一致し、すべての出力ハッシュが一致すると`reused: true`。
  設定・入力・スクリプト変更や出力の破損は再実行する。失敗・出力欠落を成功として保存しない。
- 結果はソース相対の`outputs[].path`・SHA256・サイズ。`.asset-cache/`は一時キャッシュなので.gitignoreへ入れる。
  採用する完成素材を`assets/`等へコピーし、または既存uploadツールへ登録する。配信や素材一覧でキャッシュパスを参照しない。
  レシピと基準画像はソースに残し、必要な完成素材だけ`design/game-assets.json`へ登録する。
- 1レシピの上限は入力/出力各40、1ファイル256MiB、実行180秒。stdoutは結果JSON、実行ログはstderr。
  同じレシピが実行中ならロックで重複実行を拒否する。異常終了で残ったlockは実行終了を確認してから除去する。
- このCLIはローカル加工とファイル整合性の検査。隔離・課金・美術品質・リグ/アニメの検証の代わりにはならない。
  エンジンや画像形式の互換性も実表示で確かめる。SVGはゲーム内では使えるが既存画像アップロードでは受け付けない。

## 実行と修正の順番

依存がない処理だけ並行する。原型→リグ→モーションや、生成→透過→分割は順番を守る。
MCPが返る前に並行作業できると決めつけず、pending/timeoutでは既存asset_id/run_idの結果取得へ進む。
待ち時間のたびにLLMを呼んだり同じ有料要求を再送したりしない。

まず寸法・透過・欠損・原点・骨格・必要クリップ・サイズを既存の検査で確かめる。
次に代表場面で実画像/短い動作を見て、基準との差を一つずつ直す。
「静止画が良い」と「動作/ゲーム内表示が正しい」を分ける。安い試作を全素材へ強制せず、失敗時に高い手戻りが出るものだけで使う。
既存の企画承認以外に承認待ちを足さず、確認済み/未確認を記録する。

`design/asset-manifest.md`の変更行だけへ経路・基準・再利用した原型/レシピ・必要動作・結果を追記する。
費用や時間の削減は実測なしで断定しない。既存の使用量台帳が料金の正で、CLIの実行時間からAI原価を推測しない。
