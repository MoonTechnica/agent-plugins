# ステージ・マップを作る

**体験の意図 → 進行の構造 → 空間の候補 → 遊べる仮組み → 検査と選定 → 素材化 → 再確認**。
地形の広さや素材数を品質の代わりにしない。既存の `$game-design` の工程の中で使い、
企画の合意・出力・規約・試遊の実施条件は `instructions.md` と既存 Skill に従う。
新しい承認待ちや企画ターンを足さない。コンセプト画像は方向の資料であり、実装済みマップの証拠ではない。

## 1. 適用範囲と作業の大きさ

移動経路、障害物、敵や報酬の配置、盤面の構造が遊びに影響するときに使う。
単画面やエンドレスは配置・区間の設計で十分。空間を使わないクイズ等へマップを追加しない。
地域/部屋を移動するゲームやプレイヤー用の地図を作る・変える時は
[references/transitions-and-map.md](references/transitions-and-map.md) を読む。
場所の切替、部屋単位/連続/混合の読み込み、能力による再探索、実世界と地図の対応を扱う。

- 新規/構造を変える依頼: 下の工程を必要な範囲で行う。
- 数値/不具合/装飾の変更: 変わる場所と依存する経路・進行だけを直す。全マップを再生成しない。
- 既存の定義・安定ID・seed・生成版・セーブ互換性を先に読む。新しい形式へ一律変換しない。
- 前の版に `rules.ts` が無い場合は `$game-design` の局所変更方針を守る。
  既存の移動/進行処理をそのまま検査できる範囲を調べ、利用できるプレビューでも確認する。
  検査のためだけに核を作り直さず、実行できない検査とその理由を未確認として残す。
- 貢献ブランチでは依頼に関係する変更だけ。`design/` の新規文書が不要なら、既存の記録と
  `design/playtest.md` または `build-report.json` の `notes` に必要な判断・検査を残す。

## 2. 体験と制約を決める

brief・操作・カメラ・既存の調整値から、次を短く決める。通常は `design/level-design.md` にまとめる。
小さいステージは数行と表でよく、これ以降の候補比較・修正の記録も同じ文書へ追記する。
プレイヤーの速度/ジャンプ/衝突形状が未確定なら、まず代表的な足場・通路で操作を成立させる。

| 決めること | 内容 |
|---|---|
| 体験 | 場所/区間ごとに何を理解し、選び、試し、得るか。発見・緊張・休息・驚き等から作品に合うもの |
| 進行 | 開始、主要目的、前提条件、任意の寄り道、復帰地点、次の区切り。終わりのない世界では活動の区切り |
| 移動と視界 | 移動能力、体の大きさ、カメラ、見える/反応できる範囲。PCとタッチで達成する操作 |
| 世界と地図 | 地域/部屋の接続、切替/連続/混合の読み込み、地図が必要なら実世界との対応と探索/知識の表示規則 |
| 必須条件 | 必要な場所へ到達、鍵/能力の入手順、復帰、依頼した内容、地域境界。違反候補は除外 |
| 比較する品質 | 導線、難易度の変化、選択の意味、再試行の負担、移動時間、世界観。作品に必要な軸だけ |
| 制作の枠 | 今回の範囲、候補数、修正の上限、確認するseed/経路、素材/実行予算 |

移動時間・見通し・難しさの目標はその作品の brief から置く。全ジャンル共通の密度・所要時間にしない。

## 3. 進行と空間を分ける

まず「入口 → 安全に試す → 応用 → 休息/報酬 → 次の区切り」等の体験を、部屋・区間・地点の
**意味と接続**で表す。これは例であり、ホラー、自由探索、対戦へ順序を強制しない。
鍵、扉、片道、取得能力、クエスト状態は接続の前提/結果として記す。
次に、意味を地形・座標・高さ・通路・敵/報酬・カメラ位置へ割り当てる。

- 定義データと実行中の状態を分離する。正本はゲームが実際に読むtilemap/JSON/TS等の既存形式。
  文書の接続図だけを検査してゲームの地形を合格にしない。
- 表示、衝突、移動/経路判定、配置が同じ定義を参照する。描画コードに別の地形を手書きしない。
- 3DのGLBは見た目の資産。衝突/歩行面/進行条件を別に定義し、モデルの見た目だけで到達を判断しない。
- 生成画像は画風/背景の資料に使えるが、通路・衝突・鍵の順序の正本にしない。
- 部屋/区間の小さな部品を再利用するなら、入口/出口、方向、通路幅、高低差、役割、配置禁止範囲を持つ。
  接続面が合うことと、全体を進行できることは別に検査する。

## 4. 小さな候補を比較する

構造の選択肢がある新規制作では、まず安価なデータ/図形の候補を**2〜3案程度**比較する。
これは初期の目安。明確な指定、局所修正、厳しい予算では1案でよい。
候補ごとに素材生成・別ゲーム・別ターン・Platformビルドを起動しない。

1. 開始前に必須条件と品質軸を決める。構造が異なる候補にする（一本道/分岐/ループ等）。
2. 正本の定義をゲームの移動・進行ルールで検査する。方法は [references/checks.md](references/checks.md)。
3. 必須条件を満たす候補だけで、経路/難易度/移動の負担等を比較する。
   長い経路・多い分岐・広い面積へ一律に高得点を付けない。単一の総合点で失敗を隠さない。
4. 作品に合う1案を採用し、採否の理由と失敗したseed/地点/状態を記録する。
   生成器と調整値を変える際は、同じseed・能力・初期状態で変更前後を比べる。

修正は通路幅・足場・鍵の位置・復帰地点等の最小単位から。既定は構造修正2巡程度を目安にし、
改善が止まる/予算が近い場合は規模を減らして核を成立させる。指定した主要要素を削る場合は差を説明する。
既知の進行不能を合格にせず、直し切れない条件は残る問題として報告する。
固定のAI役職や複数モデルの呼び出しは不要。生成と評価を異なる観点で行えばよい。

## 5. 仮組みから仕上げる

代表的な区間を簡単な図形/既存の軽い素材で**実際の操作・衝突・カメラ**につなぐ。
ルールの描画なし検査と、利用できる実画面/作者プレビューでの確認を分ける。
後者の環境が無ければ、未確認として軽量な方式で制作を続ける（`$game-playtest`）。

- 安全に操作を試せる導入、選択が分かる分岐、危険の予告、失敗からの復帰を確認する。
  高難度/ホラーでも危険を理不尽な入力不能や進行不能と混同しない。
- 最初に代表区間を仕上げ、必要なモジュール/素材を `$game-art-direction` の asset manifest へ反映する。
  全地域を高品質素材で埋める前に、見た目と遊びが両立することを確かめる。
  光・音・物語そのものが体験の核なら、その代表区間は早期に演出まで試す。
  図形だけでホラーの緊張や発見の魅力を検証済みとしない。
- 素材の差し替えで、通路/衝突/視界/安全地点/手掛かりが変わる場合は影響範囲を再検査する。
  装飾の形を理由なくcolliderへ流用しない。地図の全景だけでカメラ内の読みやすさを合格にしない。
- 量産では目的・組み合わせ・選択・空間の変化で区間を差別化する。色替えだけを新ステージと数えない。
- 広い世界の読み込み/解放/保存は `$game-open-world`、重い表現の試作は `$game-design`
  references/performance-risk.md、対戦のサーバー判定は `$game-multiplayer` に従う。

## 6. 検査の証拠と完了

`design/playtest.md` に本マップの観察項目と結果を書く。
`design/level-design.md` には定義/生成版・候補/seed・能力/初期状態・検査法・失敗例・採否を残す。
局所変更/貢献では§1の例外を適用し、既存の記録または `notes` だけで足りれば新しい文書を作らない。
大量の候補やログをリポジトリへ保存せず、再現に必要な小さいデータと要約だけを残す。

- 定義の整合性、必要な地点/進行の成立、対象経路のルール検査を確認した。
- 採用理由が依頼と体験に結び付いており、確認済みの重大な失敗を修正した。
- 仕上げ後の画面/操作/負荷は確認した環境・経路・版と、未確認を区別した。
- ランダム入力、接続図、画像の評価だけから「面白い」「全seedで解ける」「実機で快適」と断定しない。
- Platformの長い試遊は `$game-playtest` の明示依頼時だけ。毎候補の有料検証を自動追加しない。

返事は「どんな場所/選択を作ったか」「どの経路や進行を確かめたか」「残る未確認」を短く書く。
制作時の探索・候補評価と、実行時の自動生成は別。依頼にない無限生成や難易度の自動変更を導入しない。
