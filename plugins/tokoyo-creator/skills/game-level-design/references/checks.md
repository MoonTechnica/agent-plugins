# マップ検査を遊びに合わせる

`$game-level-design` の候補比較と仕上げ後に、該当する節だけ読む。
チェックの入力は**ゲームが読む定義と実際の移動/進行ルール**。独立の図を合格させない。
追加の外部ライブラリは不要。既存のルール検査へ必要な性質を加える。

## 1. すべての空間

- 参照ID、座標/サイズの有限値、境界、配置の重複、開始/目的/復帰地点の有効性。
- 通路は点でなくプレイヤーの幅/高さで通れるか。表示と衝突・通行属性が一致するか。
- 必須地点への到達。意図した未到達領域（背景/後で開く地域）と不具合を区別する。
- 片道移動後、死/失敗/保存再開後、地域を再訪した後も進行できるか。
- 実画面ではプレイヤーのカメラから分岐・目的・危険の手掛かりが読み取れるか。
  スマホ幅でHUD/操作部が通路や敵を覆わないか。色だけに頼らない。

検査結果は `pass / fail / unknown` を区別し、検査した入力と反例を残す。
探索に上限を置き、打切りを到達不能や合格と扱わない。

## 2. 地上移動・探索

壁/通行可能セルだけのゲームはBFS等で開始から必要地点への接続を調べる。
連続空間では体の幅を考慮した移動領域を使い、地図上の直線距離を通行可能距離と扱わない。
通路/高低差/段差/片道/ロード境界は移動ルールに沿う。
最短経路を求めるときは手数/距離/時間のどれかを決める。BFSの最少遷移は移動コストが等しい場合だけ最短で、
距離/時間が異なる経路は実コストを使う探索で比較する。

接続していることに加えて、主経路の移動時間、目的のない往復、手掛かりの見える位置を観察する。
探索では常に最短経路へ誘導せず、寄り道の発見や戻る価値を作品の意図に合わせる。

## 3. 鍵・能力・クエスト・パズル

「場所」だけでなく、**場所＋所持品＋解除状態＋進行**を探索状態にする。
鍵が扉の先、片道の先に必要能力、報酬の二重取得、押した箱が復帰不能等の反例を調べる。

例（図ではなく正本の配置とルールで判定）:

```text
入口 → 広場 → 扉 → ゴール
        ↘ 鍵の部屋 ↗
扉の前提: 鍵を持つ。鍵の部屋から広場へ戻れる。

成功の経路: 入口 → 広場 → 鍵の部屋 → 広場 → 扉 → ゴール
反例: 鍵をゴールへ置くと進めない。
反例: 鍵の部屋が片道の袋小路だと鍵を取得しても戻れない。
```

消費鍵・動く箱・スイッチのON/OFFは単純な「到達した能力の集合」では扱えない。
既存の `step` 等で状態遷移を探索/再生する。大きい状態空間は上限付きの重要ケース検査に留め、
全状態での非詰みを保証したと書かない。復帰/リセットの挙動も実ルールで確認する。
同じ位置でも取得状態が違う場合を同じ訪問済みにまとめない。

## 4. プラットフォーマー・コース・エンドレス

- 空中を通行可能としてflood fillしない。ジャンプ・着地・落下・速度・プレイヤー幅をルールで再生する。
- 跳躍距離の数式は候補除外の目安。実際のdt/加速/衝突/coyote/buffer/頭上障害を含む検査と分ける。
- 許される操作で足場から次の足場へ到達する入力列を残す。検査専用teleportや無敵で進行を証明しない。
- タッチで要求される同時押し、着地の余裕、カメラに見える予告時間を確認する。
- エンドレスでは区間単体だけでなく入口速度/出口状態と前後の接続を検査する。
  生成方式の版＋seed＋区間番号で失敗を再現し、先頭/難易度境界/最速域を含める。

## 5. 対戦・戦闘アリーナ

有効な開始地点、相手/目標への経路、即死配置、遮蔽物、危険/有利地点、復帰位置を確認する。
各slotから目標/資源への到達時間、射線、逃げ道、合流地点を比較する。
対称地形は公平性の証明ではない。非対称でも意図した役割/人数/装備なら成立し得る。
各slot/役割と、想定した最少/最多人数をサーバーのルールで検査する。
強いbotの勝率だけを人の公平性と扱わない。実対戦で未検証ならその範囲を残す。

## 6. 手続き生成・広い世界

地域/部屋の切替とプレイヤー用地図がある場合は、このSkillの `references/transitions-and-map.md` §6も検査する。
この節のseed検査は、作者が固定したマップへランダム生成を追加する指示ではない。

生成器を使う場合のみ、固定の回帰seedと別の探索seedを有限数で検査する。
例えば最初は各4程度から始め、検査コストと重要性に応じて調整する。全seed保証ではない。
失敗したseedは修正後も回帰ケースとして保持し、比較に使わなかったseedも確認する。

- チャンクを異なる順序で生成/再訪しても境界・安定ID・必要な地点が一致する。
- 接続部品の局所的な整合性だけでは、全体の目的や鍵の順序は保証できない。
- 再生成に上限を置く。失敗時は検査済みの固定区間/安全な接続等に戻し、無限の再抽選をしない。
  代替案も同じ必須条件で検査する。安全な結果を得られなければ失敗を伝える。
- 探索の幅/量と、同時読み込み/保持/活動NPCの負荷を別に扱う（`$game-open-world`）。

## 7. 記録例

```markdown
定義: godot/levels/forest.tscn / 生成版2 / 今回のcommit
操作: 歩行3m/s、幅0.6m。鍵は消費しない。
必須: 鍵→扉→目的地、失敗後の復帰。品質: 選択と移動負担。
枠: 2候補、修正2巡。固定seed 4 / 別seed 4。

| 案 | 必須条件 | 品質の観察 | 採否 |
|---|---|---|---|
| A 一本道 | pass（進行の状態探索） | 同じ道を長く戻る | 不採用 |
| B 短いループ | pass（進行の状態探索） | 鍵の後に近道、寄り道は任意 | 採用 |

修正: seed 17で入口の幅不足→入口モジュールの寸法を修正、同seedで再検査。
実画面: 未確認（描画環境なし）。地図の俯瞰から視認性を合格にしない。
```

これは記録の例。未実施の数値/seed/合格を写さず、実際の検査を `design/playtest.md` と照合する。
