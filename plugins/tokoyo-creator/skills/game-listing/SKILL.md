# 掲載情報（公開ページに出るもの）

ゲームのページ・一覧・共有のカードに出る情報を、**ソースの `listing/`** に置く（配信物 `dist/` には入れない）。
**そろっていない版は公開できない**。利用者はここを見てゲームを選ぶので、ゲームの中身と食い違わないこと。

```text
listing/
├── listing.json   # 文字の項目
├── icon.png       # アイコン（正方形。.webp も可）
└── cover.png      # カバー画像（横長。.webp も可）
```

## 1. まず今の掲載情報を読む

`./input/listing.json`（手元では `get_app` の `listing`）が**今の掲載情報**。
ソースの `listing/listing.json` より**こちらを優先する**（利用者が画面で直した値はこちらにしか無い）。

| キー | 意味 |
|---|---|
| `title` `tagline` `description` `howToPlay` `category` `tags` | 今の値（空なら未作成） |
| `hasIcon` / `hasCover` | 今の版にアイコン / カバーがあるか（画像そのものはソースの `listing/` にある） |
| `userEdited` | **利用者が手で直した項目**（`title` `tagline` `description` `how_to_play` `category` `tags`） |
| `missing` | **公開に足りない項目**（`icon` `cover` を含む）。このターンで必ず埋める |

**最初に `listing/listing.json` を、`input/listing.json` の値で書き直してから**作業を始める（ソースの古い値で
利用者の手直しを上書きしないため）。

## 2. このターンで何をするか

| 状況 | すること |
|---|---|
| **企画のターン**（コンセプトを見せて返す。`$game-art-direction` §2） | **何もしない**（掲載情報も `releaseNotes` も作らない。ゲームができてから書く） |
| **初回**（前の版が無い・`missing` が全部） | 全項目を作る（§3・§4） |
| `missing` がある | その項目を作る |
| 遊びの中身が変わった（操作・ルール・目的・モード・人数・対戦の有無が変わった） | `description` と `howToPlay` を直す。ジャンルが変わるほどなら `category` も |
| 見た目が大きく変わった（主人公・世界観・絵柄を替えた） | `icon` と `cover` を作り直す |
| ゲーム名を変更した | 独立ロゴを更新し、`icon` / `cover` を再合成する。スタート画面も同じロゴへそろえる（手直しされた名前は今の掲載情報を優先） |
| 利用者が名前・説明などの変更を頼んだ | 頼まれた項目を直す（`userEdited` にあっても。§5） |
| 色の調整・不具合の修正・難易度の微調整など | **何も変えない**（掲載情報に書いていない細部は直さない） |

- **直す必要があるかは、このターンで何を変えたかから判断する**。毎ターン書き直さない
  （同じことを言い換えるだけの変更は、利用者から見ると理由の無い変更になる）。
- **`userEdited` の項目は、利用者が依頼文で変更を頼んだとき以外は変えない**。遊びが変わって説明が合わなくなっても、
  変えずに `build-report.json` の `notes` に「説明（利用者が直した）が新しい遊び方と合っていません」と 1 行書く。
- 直したら、何を直したかを `notes` に 1 行書く（例: 「2 段ジャンプを足したので遊び方を更新」）。
- **`releaseNotes` だけは版を作るターンで毎回書く**（上の表の「何も変えない」ターンでも。企画のターンは除く）。先頭に
  `## 空の光と色を大気散乱で改善` のような**変更内容を表す短い見出し**（目安 15〜40 文字、最大 100 文字）を付ける。
  この見出しは作業履歴と提案の題名に自動設定される。依頼文をそのまま引用せず、実際にできた変更を要約する。
  見出しの後に空行を入れ、この版で何が変わったかを遊ぶ人に向けて 1〜3 行で書く（「敵が 3 種類になった」「スマホで跳びにくかったのを直した」）。前の版の `releaseNotes` は引き継がれないので、
  前の文を残さず、このターンの変更だけを書く。提案の説明にも自動入力されるので、何を変えたかと、なぜ変えたかを具体的に書く。エンジン移行・リファクタ・ビルドの修正だけの版でも省略せず、その内容と目的を書く。実行していない検証を成功したと書かない。

## 3. 文字の項目（`listing/listing.json`）

```json
{
  "title": "ねこジャンプ",
  "tagline": "屋根から屋根へ、跳んで避けろ！",
  "description": "夜の街を駆ける黒猫になって…（本文）",
  "howToPlay": "【目的】…\n【PC】スペースで跳ぶ\n【スマホ】画面をタップで跳ぶ\n【コントローラー】A ボタンで跳ぶ",
  "category": "action",
  "tags": ["猫", "反射神経", "ハイスコア"],
  "releaseNotes": "## 敵の種類を追加し、スマホのジャンプ操作を改善\n\n敵が 3 種類になった。スマホで跳びにくかったのを直した"
}
```

| キー | 文字数 | 書き方 |
|---|---|---|
| `title` | 1〜30 | ゲームの名前。遊びが伝わる短い名前。副題を付けてよい（「ねこジャンプ 〜夜の屋根〜」）。「〇〇ゲーム」「無題」にしない |
| `tagline` | 1〜40 | 一覧のカードに出る一言。何をするゲームかと魅力を 1 文で |
| `description` | 1〜1000 | ゲームの紹介。世界観・遊びの流れ・見どころ・モード（ソロ / 対戦 n 人 / 練習モード / ランキング）。改行してよい |
| `howToPlay` | 1〜800 | **目的**と、**PC・スマホ・（対応していれば）コントローラー**それぞれの操作。実装した操作と一致させる（`$game-controls`） |
| `category` | 下の一覧の id | 最も近いもの 1 つ |
| `tags` | 0〜5 個・1 個 1〜20 文字 | 題材・雰囲気・特徴（「猫」「ドット絵」「協力プレイ」）。`#` は付けない。ジャンル名の繰り返しは入れない |
| `releaseNotes` | 1〜2000 | **この版で変わったこと**（§2）。ゲームのページの「この版で変わったこと」と、公開のお知らせに出る |

- 文言は日本語（`instructions.md` §6）。誇張しない（「世界一」「無料で稼げる」など、中身と違うことを書かない）。
- 実在の作品・ブランド・人物の名前を使わない（利用者が自分の作品として頼んだものを除く）。

**ジャンル（`category`）の一覧**:

| id | ジャンル | id | ジャンル |
|---|---|---|---|
| `action` | アクション | `strategy` | ストラテジー |
| `shooter` | シューティング | `board_card` | ボード・カード |
| `platformer` | 横スクロール・ジャンプ | `rhythm` | リズム・音楽 |
| `puzzle` | パズル | `quiz` | クイズ・ことば |
| `racing` | レース | `casual` | カジュアル（ワンタップなど） |
| `sports` | スポーツ | `party` | パーティー（みんなで遊ぶ） |
| `rpg` | RPG | `other` | その他 |
| `adventure` | アドベンチャー・探索 | | |
| `simulation` | シミュレーション・育成 | | |

## 4. 画像

| 画像 | 形 | 何を描くか |
|---|---|---|
| `icon.png` | **正方形**・512〜2048px・PNG か WebP・4 MiB まで | ゲームアイコン専用の構図。主役の顔・特徴的な道具・ゲームを象徴する物を 1 つ、大きく見せる。小さくても輪郭と色で識別できるようにする。独立したタイトルロゴを原則下部に合成する。角は Platform が丸めるので背景を四隅まで塗る |
| `cover.png` | **横長**（幅 / 高さ 1.4〜1.9。16:10 を推奨）・幅 1200〜2560px・PNG か WebP・4 MiB まで | トップバナー用のキービジュアル。ゲームの世界と主役に加え、**独立した透過タイトルロゴを合成する**。タイトルと主役が切り抜き後も残る構図にする |

- 絵柄はゲームの中の絵とそろえる（ゲームで使ったキャラクター・配色・画風をそのまま使う。`$game-asset-tools`）。
- `design/concept/key-art.png`（`$game-art-direction` §1）があれば、カバーの参照画像に使う。`hero.png` があればアイコンの参照画像に使う。
  キャラクター・配色・画風を引き継ぎ、**バナーとアイコンはそれぞれの用途に合わせて生成する**。コンセプト画像を切り抜いただけで完成にしない。
- ゲーム画面のスクリーンショットをそのまま使わない（検証の記録は Platform が別に撮る）。

### 構図と生成プロンプト

**先にゲーム名を確定する**。独立した透過ロゴの生成・素材登録・合成・再利用は
[references/title-logo.md](references/title-logo.md) に従う。ロゴ → 文字なしの用途別ビジュアル →
i2iまたはローカル合成の順に作り、画像ごとにタイトルを描き直さない。
採用済みキャラクター画像と独立ロゴを参照したi2iで、完成画像を直接作る方法も使える。
キャラクターを使う場合は実際の採用素材を参照し、顔・衣装・特徴とロゴの文字を生成後に照合する。
主役はキャラクターに限らず、車・建物・道具・盤面などゲームを象徴する対象を選ぶ。
アイコンは原則下部にロゴの余白を設け、象徴と世界観が小さくても伝わる構図にする。
カバーは中央の安全な範囲に主役と同じロゴを配置し、切り抜き後も全文を読めるようにする。
説明文・操作UI・架空の賞やストアのバッジを描き足さない。

**文字なしのビジュアルは `generate_image` で作る**（画像の枠を 1 回ずつ使う。透過ロゴは別に作って再利用する）。アイコンは `size="square"`（1024×1024）、カバーは
`size="landscape"`（1536×1024）で作り、`download_url` から取って `source/listing/` に置く（どちらもそのまま条件に合う。
透過しない画像は WebP で届くので、拡張子は `.webp` にする）。

完成アイコンとカバーの置き場所はソースのプロジェクトの直下の `listing/`（`package.json` と同じ階層）。ソースの commit に含める（§2 の出力）。

**生成後は、保存する最終画像を画像表示ツールで開いて確認する**（リサイズ・切り抜きをした場合は処理後の画像）。
バナーはタイトルの誤字・欠け・不要な文字・背景への埋もれ・主役の見切れを確認し、16:10 の表示でも読めることを確かめる。
アイコンは 48px / 96px の縮小表示と丸角表示でも主役が判別できるか確認する。
不備があればプロンプトや配置を修正して作り直す。画像生成が使えない・修正しても整わない場合は、未確認の画像を完成扱いせず `notes` に理由を残す。

## 5. `listingRequested`（利用者が頼んだ変更）

`userEdited` にある項目を、**利用者が依頼文で変更を頼んだので**変えたときだけ、`build-report.json` に挙げる。
挙げない限り、Platform は `userEdited` の項目を前の値のまま残す（変えても反映されない）。

```json
{ "manifest": { … }, "buildConfig": { … }, "notes": ["頼まれたので名前をキャットホップに変更"], "listingRequested": ["title"] }
```

- 名前は `title` `tagline` `description` `how_to_play` `category` `tags`（DB の名前。`howToPlay` ではなく `how_to_play`）。
- 頼まれていない項目を挙げない。

## 6. チェック

- [ ] `listing/listing.json` を `input/listing.json` の値から始めた
- [ ] `missing` の項目をすべて埋めた（`icon` `cover` を含む）
- [ ] `title` は 30 文字・`tagline` は 40 文字・`description` は 1000 文字・`howToPlay` は 800 文字以内
- [ ] `howToPlay` の操作が、実装した操作（PC・スマホ・コントローラー）と一致している
- [ ] `category` は一覧の id、`tags` は 5 個まで
- [ ] `icon` は正方形（512〜2048px）、`cover` は横長（幅 1200〜2560px・比 1.4〜1.9）
- [ ] 独立した透過ロゴを素材一覧に登録し、アイコン・カバー・スタート画面で同じ素材を再利用した
- [ ] 最終画像を開いて確認した。バナーのタイトルは最終的な `title` と一致し、16:10 表示でも全文が読める
- [ ] アイコンは専用の構図で、48px / 96px・丸角表示でもゲームの特徴が分かる。バナーと主役・画風・配色が一致している
- [ ] `userEdited` の項目は、頼まれたとき以外は変えていない。変えたなら `listingRequested` に挙げた
- [ ] `releaseNotes` の先頭に変更を要約する短い見出し（100 文字以内）を付け、その後に変更内容と理由を書いた（全体 2000 文字以内）
- [ ] 変えた項目と理由を `notes` に書いた（変えていなければ書かない）
