# スタート画面の開始・再開・設定と状態

開始画面を作る/変更する時に読む。構図は `$game-screen-layout` §5、美術は `$game-art-direction` §6.1、
入力の解禁は `$game-controls` §3、制作中の実画像確認は `$game-playtest` references/visual-observation.md。
既存ゲームは現在の美術と構造を土台に局所修正する。単一のテンプレートに置き換えない。

タイトルは `$game-listing` references/title-logo.md の独立した透過ロゴを再利用する。
`godot/assets/title-logo.png` を `preload("res://assets/title-logo.png")` で読み（`TextureRect`）、背景・開始操作と分離して配置する。
掲載画像からロゴを切り抜いたり、画面ごとにロゴを再生成したりしない。

## 1. 最も使う操作を主役にする

- 初回は「遊ぶ」/「新しく始める」。有効な保存がある進行型は「続きから」を主操作にし、復帰先を短く添える。
  保存なしの「続きから」を無効状態で主操作にしない。クリア済みは実際の続きを確認し、再挑戦/章選択などを選ぶ。
- 主操作と補助操作は強さを分ける。設定・操作ガイドを押しただけで開始しない。起動演出で入力受付を遅らせない。
- 準備済みの短時間ゲームは1操作で開始。新規世界作成や対戦参加等の必要な選択は明示する。
  「タップしてタイトル」→「メニュー」→「開始」のような意味のない確認段階を増やさない。
- Enter/Spaceは選択中の項目を決定する。設定やガイドを表示中は背景の開始に入力を渡さない。
  連打で開始/接続を重複させず、開始に使った押下・保持をプレイの攻撃/移動へ誤転送しない。
- ゲームパッド対応時は選択可能な主操作にカーソルを置く。入力方法を変えても、選択位置と決定/戻るの意味を保つ。
  音声解禁・iframeフォーカスの最初の操作は `$game-controls` §3 の制約に従う。

## 2. ジャンルから必要な機能を選ぶ

| 遊び | 主操作 | 必要な場合だけ付けるもの |
|---|---|---|
| 短時間アクション/スコア競争 | 遊ぶ | 自己ベスト、短い目的、「操作方法」 |
| パズル/ステージ型 | 次のステージ/続きから | ステージ選択、進行表示 |
| RPG/探索/物語 | 続きから（保存なしは新規開始） | 復帰先、ロード、字幕、難易度 |
| 対戦/協力 | 対戦を探す/参加する | 部屋作成、招待、接続状態、待機取消。ソロがあれば入口も分かるように |
| サンドボックス/制作型 | 世界を開く/続きから | 世界選択、新規作成 |

機能があるという理由だけで全項目を並べない。ランキング/ショップ/実績/クレジットは依頼と遊びに必要な場合だけ。
Hostの退出/全画面/共有導線を重複させず、PC向けメニューのQuitをブラウザのタブ終了として移植しない。

設定は開始前にも任意で開ける。音・入力・表示・動きのうち実在する項目を扱い、ポーズ中と同じ状態/保存処理を使う。
設定から戻ると元の主操作/選択へ戻る。初回設定や操作説明を読むことを、開始の必須条件にしない。
操作の説明は開始画面に並べず、補助項目「操作方法」から開く専用画面に置く（中身は `$game-controls` references/godot-input.md §4）。
目標が絵だけでは伝わりにくい時は「何を達成する遊びか」を一言添える。全機能の長い説明は開始画面に置かない。

## 3. 起動状態を混同しない

| 状態 | 表示・処理 |
|---|---|
| 保存を確認中 | 確認中。保存なしと決めつけて新規保存で上書きしない |
| 保存なし/有効な保存あり | 確認結果に従って新規開始/続きからを選ぶ |
| 保存取得失敗/使用できない保存 | 理由と再試行。読み込み失敗を保存なしと扱わず、元データを保つ |
| 素材の準備中 | 測れる進捗または現在の準備段階。使えない主操作には理由を示す |
| 開始可能 | 同じ位置の主操作を開始可能にする。未操作のまま勝手に本編へ移らない |
| 開始/接続失敗 | 元の選択を保ち、再試行/戻る。終わらないスピナーにしない |

保存を持たない短時間ゲームに保存機能を追加する指示ではない。
有効な保存を上書きする新規開始には、失う進行を示す確認を置く。普段の開始/続きからには不要な確認を挟まない。
音の有効化に失敗しても無音で開始でき、音の設定は維持する。失敗はログと必要な画面表示で扱う。
初回ステージを遊ぶために不要な全ステージ/全素材の取得を待たせず、既存の先読みを使う。

## 4. よくある失敗を避ける

開発用ビルドの通常開始は、本編と同じ入口・開始/再開・設定処理を共有する。開発panel/overlayの入口は補助操作として
配置し、開く/閉じる操作を本編の開始へ伝播させない。タイトル/ポーズへの入口は作品に合わせて選び、
全作品の開始メニューへ同じ開発項目を追加しない。ステージ直行は明示した開発caseで扱う。
開発ケースの準備・ready・通常試遊復帰は `$game-playtest` references/development-preview.md。

| 失敗 | 修正 |
|---|---|
| 説明文と同じ見た目の「スタート」文字だけ | 押す対象と選択状態が明確な主操作にする |
| 全項目が同じ大きさ/強い色 | 開始/再開を強くし、補助項目の階層を下げる |
| 設定/ミュートのクリックが開始も発火 | 音の解禁と開始の決定を分け、操作先を判定する |
| 初回から使えない続きからが選択中 | 有効な保存を確認し、選べる項目へ選択を移す |
| 読み込み後にボタンが別の位置へ移る | 準備中から主操作の置き場を確保する |
| 横長画面を縮めてスマホへ表示 | 絵とメニューを組み替え、文字/操作部の物理的な大きさを保つ |

## 5. 変更した画面を確かめる

`design/playtest.md`へ今回該当する項目を加える。通常の制作中の短い観察を使い、thoroughを勝手に追加しない。

- 初回の主操作、進行型の再訪と復帰先、保存確認中/失敗の扱い。
- 設定を開く→変更→戻る→開始。ミュートやガイド操作で開始しないこと。
- 準備中→開始可能、失敗→再試行、連打と開始後の最初の一手。
- タッチ/マウス/キー、対応時はゲームパッドの選択・決定・戻る。
- 390×844 / 844×390 / 1440×900と実際の枠で主役/文字/操作が隠れない。動き軽減・無音でも分かる。

最初は変更に関係する重要な1〜2場面を観察し、局所修正後に同条件で再確認する。
隔離試遊の新しいブラウザや保存スタブでは永続保存/再訪の証拠にならない。
実際に確認できない状態は未確認と記録し、架空の保存や成功画像で合格にしない。
起動の成功は操作の成功、撮影の成功は美術の合格を意味しない。
