# 見た目の方向と素材の設計

絵は作る前に**方向を 1 つに決めて**から量産する。素材を 1 枚ずつ思いつきで作ると、主役・敵・背景の絵柄がばらばらになる。
道具の呼び方（生成・透過・取り込み・モデリングの手順）は `$game-asset-tools` と `$game-3d-studio` にある。この Skill は**何をどの経路で作るか**を決める。

**素材の配色だけでなく、組み合わせたプレイ画面までディレクションする。** 最初に
[references/visual-direction.md](references/visual-direction.md) の §1〜§3 を読み、2D は §4、3D は §5、仕上げは §6 を読む。
マップ・ステージ・世界を作る作品は [references/concept-to-map.md](references/concept-to-map.md) も読み、コンセプトを変換表に書き下ろしてから素材と照明を決める。
利用者の指定と既存の作品の基準を優先する。ジャンル名から固定プリセットを当てない。

## 1. コンセプト（`design/concept/` と `design/style-guide.md`）

コンセプト用の素材にも§3の評価順を適用する。適合する素材を使った構図・Blenderでの描画で方向を示せるか判断し、固有の見た目を表せない場合に画像生成を選ぶ。以下の画像生成手順は生成を選んだ場合に使う。
**どの経路でも、企画のターンには `key-art.png` と `hero.png` の実物を必ず置く**（チャットのカードに並ぶのはこの名前の画像だけ。
画像が無い企画は、利用者が世界観を確かめられない）。

| ファイル | 中身 |
|---|---|
| `key-art.png` | **プレイ画面の構図を想定した完成イメージ 1 枚**。主役・敵・背景・HUD の位置、画風・光・雰囲気を共有する。未実装のコンセプトで、実ゲームのスクリーンショットとは説明しない。文字は入れない。掲載カバーへ使う時は `$game-listing` のタイトル/構図に合わせる |
| `hero.png` | 主役と主な敵 2〜3 体を**同じ縮尺**で並べた 1 枚（単色の背景・正面か側面）。以後の主役の絵はこれを元にする |
| `title.png`（任意） | タイトル画面の構図を共有する見本 1 枚。既存の絵/実場面で方向を共有できるなら追加生成しない。文字と操作部は実装で重ねる |
| `map.png`（空間が遊びの中心の作品） | **全体図**。広い世界・ダンジョン・複数の部屋/ステージ・RPG のフィールド・対戦マップなど。画像生成で作らず、`design/world-map.json` から `$game-level-design` references/world-layout.md のツール（`overview --concept`）で描く。番号の名前は `level-design.md` に書く |
| `style-guide.md` | 下の 5 行（3D は + 3 行）を入口に、作品の明暗・質感・光・カメラ・UI / VFX の基準を必要に応じて追記（references §2） |

- 画像は **PNG か WebP・長辺 1024px 以下・1 枚 1 MiB 以下・4 枚まで**（`key-art` `hero` `title` `map` の名前だけがチャットに並ぶ。
  4 MiB を超えた画像は Platform が黙って落とす）。
- `generate_image`（`size="landscape"` か `"square"`）で作り、`download_url` から取って `source/design/concept/` に置く。

```markdown
- 絵柄: 16px 単位のドット絵、輪郭は外周だけ
- 色: #1B1F3B #F2C14E #F78154 #4D9078 #F4F1DE（背景は暗く、触れる物は明るく）
- 形: 丸くて柔らかい。敵は三角を含む
- 光と影: 光源は左上、影は 1 段だけ
- 使わない: 文字、グラデーション、写真風の質感
（3D のとき）
- 比率: 3 頭身
- ポリゴン: キャラ 2,000 以下、小物 300 以下
- 材質: 単色 + 平らな陰影（テクスチャを貼らない）
```

- 素材のパックで揃うなら、絵柄の行にパックを書く（「Kenney Pixel Platformer に合わせる」）。パックを画風の基準にしても、ゲームの明暗・光・カメラは別に決める。
- マップのある作品は、コンセプトを作ったら `look.gd palette` で `design/palette.json` を作り、style-guide に「マップへの変換表」（地域ごとの地面・壁・色・小物と密度・光と霧・見通し）を書く（references/concept-to-map.md §2）。
- 画像生成の指示文は `design/prompts/<名前>.md` に保存する。次のターンも同じ文で作る。**全ての生成の指示に style-guide の 5 行と、その素材に関係する詳細基準を入れる**。
- 作成したコンセプト・設定画・参考画像は、`$game-asset-tools`の素材一覧に
  `purposes:["reference"]`で記録する。企画ターンでも資料の実在するファイルをcommitする。
  key-art/hero/title/mapのIDは`concept-key-art`/`concept-hero`/`concept-title`/`concept-map`。
  背景・掲載カバーとして採用する場合は同じ項目へ`game`の用途を追加する。
- 利用者が絵柄・キャラ・参考画像を示していれば、それが方向になる（添付の扱いは `$game-asset-tools` §9）。
- **コンセプトは雰囲気の共有と制作基準。** 見せる前に画像を開き、主役・場所・カメラ・明暗が依頼に合うか確認する。
  画像とstyle-guideの対応（何の形/光/構図で狙う感じを出すか）を残し、承認後の素材/代表場面でも参照する。
  実装結果との差があれば、その場所と理由を記録して近付ける。未確認の美術品質や実装済みの機能をコンセプトから主張しない。

## 2. 作る前に利用者へ見せるか（checkpoint）

見た目と遊びの方向が利用者の想像とずれていると、作り終えてから全部作り直すことになる。**方向が決まる場面では、絵ができた時点で見せて返す**。
見せるのは**具体的に見られる結果**（コンセプト画像 + brief）で、質問だけを返さない。

| 状況 | すること |
|---|---|
| 新しいゲーム（前の版が無い） | 見せて返す |
| 見た目の方向が変わる（絵柄・主役・世界観を替える）、または遊びの核が変わる | 見せて返す |
| 依頼が短く、読み方で見た目や遊びが大きく変わる | 見せて返す |
| 利用者が「確認なしで最後まで」「おまかせで」と言っている | 見せずに作り進める（コンセプトは作る） |
| 利用者がコンセプトを承認した（「これで作って」など）、または差し戻しを直すだけ | 直したコンセプトで作り進める（差し戻しが見た目の方向そのものなら、直して再び見せる） |
| 数値・不具合・細部の修正、前の版と同じ見た目で済む | コンセプトは作らない。作り進める |

**見せて返すとき（手元）**: `source/design/concept/` の画像のパスを並べ、brief の要約（一文の遊び・動詞・絵柄・作らないもの）を 3〜4 行で示して、
この方向でよいかを利用者に聞く。承認されたら同じ会話で §3 から続ける。**絵を作る前に質問しない**（見られる物を先に作る）。

## 3. 何をどの経路で用意するか（判定表）

素材の新規制作・変更は`$game-asset-tools` references/efficient-production.mdの手順を使う。
画風の基準とキャラの基準を別々に選び、現行の承認済み画像のパス/IDと維持する特徴をmanifestに短く残す。
必要な画風・動作がそろうパック、既存レシピ、共通リグをまとまりで評価し、足りない差分だけ制作する。
追加学習・外部サービス契約・共有ライブラリが存在すると推測しない。

**基本の評価順は「アセットライブラリ → Blenderでのモデリング → 生成AI」。採用を強制する順位ではない。** 利用者の指定・承認済みのデザイン、素材の役割と品質を先に満たす。利用者の提供素材と前の版の適合する素材は `$game-asset-tools` §1 で確認し、新たに必要な素材には次の順で判断する。

1. **まずMCPで調査する。** `search_stock_assets` で用途・形・絵柄・必要な動作に合う候補を探す。主役も検索対象だが、候補があるだけでは採用しない。外見・シルエット・比率・世界観・リグ／クリップ・形式・端末での負荷・ライセンスが要件に合うか確認してから `import_stock_asset` で取り込む。
2. **合う素材が無ければ、簡単にモデリングできるか考える。** 箱・樽・机・建物・単純な乗り物など、プリミティブの組み合わせや短いbpyスクリプト、既存素材の適切な調整で必要な品質に届くなら `$game-3d-studio` を使う。複雑な顔・髪・衣装・有機的な造形を粗いモデリングで済ませない。
3. **それでも難しいものには生成AIを使う。** 固有キャラや複雑な造形など、モデリングでは必要な品質に届かない・修正や制作の負担が大きい場合は画像／3D生成を選ぶ。素材が合わない理由とモデリングの適否を判断すればよく、失敗作を一度作ったり、検索を延々続けたりする必要はない。

**identity**（作品の顔: 主役・固有の敵やボス・キーアート・アイコン・カバー・世界観のある背景）は固有性を重視し、**functional**（UI・タイル・汎用の敵や小物・効果音）は役割への適合を重視する。どちらも上の順で評価する。重要キャラを「人型だから」という理由で汎用キャラに差し替えたり、固有の形や衣装が必要なのに色替えだけで済ませたりしない。承認済みの主役や絵柄を素材の都合で変えない。適切な素材を十分に調整して要件に届く場合は再利用できる。

これは素材の調達・造形の評価順であり、**リグ・モーションの品質を下げる規則ではない**。選んだモデルに必要な動きが既にあれば再利用し、不足する動きは対応する専用AIとBlenderでの調整を選ぶ（`$game-3d-studio` §4.3）。2Dの絵や音などBlenderが適さないものは、その工程を省いて生成・描画・合成を判断する。コードで済む図形・UIには素材ファイルを増やさない。以下の表は上記の判断を適用する例。

### 3.1 2D（画像）

| 役割 | 既定 | 次の候補 |
|---|---|---|
| 図形・文字・ボタン・弾・パーティクル・床の色面 | **描く**（GodotのNode2D / Control） | — |
| UI・アイコン・入力の表示・カーソル | **素材**（UI Pack / Input Prompts） | 描く |
| タイル・背景の部品・汎用の小物・汎用の敵 | **素材**（スタイルガイドのパック 1 つ） | 生成（パックに無い形だけ） |
| 汎用キャラの歩き・跳び・攻撃の連番 | **素材**（連番のあるパック） | 生成（`$game-asset-tools` §3.1 の連番の手順） |
| **主役・固有の敵 / ボス・キーアート・アイコン・カバー・世界観のある背景** | 素材を調査し、必要な固有性を満たせるか評価 | 合わなければ生成（透過が要る物は透過 PNG）。既存3Dの描画で絵柄が合う場合はその経路も評価 |
| 3D の資産があるゲームの 2D スプライト | **3D から書き出す**（`$game-3d-studio`） | 生成 |

素材はあるが絵柄が合わないときは、別のパックや適切な調整で要件を満たせるか考える。利用者が指定・承認した絵柄を、素材を使うために変えない。

### 3.2 3D（モデル・動き）

| 役割 | 既定 | 次の候補 |
|---|---|---|
| 環境（建物・木・道・地形の部品）・小物・乗り物 | **素材**（Kit 1 つ） | モデリング（Kit に無い形だけ） |
| 汎用の人型キャラと基本の動き | **素材**（外見・体型・動作が合うアニメ付きキャラ） | モデリング + 適切なリグ・動き |
| 固有の主役 / ボス | 素材を調査し固有性を評価 → 必要な品質で**モデリング**できるか判断 | 難しい造形は画像 → 3D の生成（ツール一覧に `generate_model_3d` があるとき） |
| 選んだモデルに不足する動き | 体型・動作に合う既存クリップを調査 | 対応する専用AI（人型の `generate_motion` / 体型別の `animate_model_3d`）とBlenderで補う。必要な動作を別の動作で代用しない |
| 陰影の焼き込み・テクスチャの変換 | **モデリング**（ベイク・KTX2） | — |

### 3.3 音

| 役割 | 既定 | 次の候補 |
|---|---|---|
| 効果音（押す・良い・悪い・行為ごと） | **素材**（Impact / Interface / UI / RPG の効果音） | 生成（素材に無い音）/ Godot の `AudioStreamGenerator` での合成 |
| 勝ち・負けの短い曲 | **素材**（Music Jingles） | 生成 |
| BGM（ループ） | **素材**（雰囲気・テンポ・ループが合う曲をMCPで調査） | 合う曲が無ければ生成 / Godot での合成。Blenderは対象外 |

## 4. 素材の設計書（`design/asset-manifest.md`）

**調査・経路の評価をしてから書き、作ったら「済」を付ける。この表に無い素材は作らない。** 「理由」には候補の採否とモデリングの適否を短く書く。重要素材では固有デザインを満たせるかも記録する。生成を選んだ場合は、ライブラリとモデリングで要件に届かない理由を残す（2D・音ではモデリング対象外と書けばよい）。

```markdown
| 項目 | 役割 | 経路 | 出典 | 理由 | 枠 | 済 |
|---|---|---|---|---|---|---|
| 主人公（透過・右向き） | identity | 生成 + 透過 | prompts/hero.md | 検索候補は顔・衣装が不一致。平面のイラストでモデリング不適 | image 2 | ✓ |
| 敵（歩き 4 コマ） | functional | 素材 | Platformer Characters | 連番あり・パック統一 | stock 1 | ✓ |
| 床タイル | functional | 素材 | Pixel Platformer | パック統一 | stock 3 | ✓ |
| スコア・ボタン | functional | 描く | — | 画面に追従 | — | ✓ |
| 効果音 3 種 | functional | 素材 | Impact Sounds | 十分 | stock 3 | ✓ |
| BGM | functional | 生成 | prompts/bgm.md | 検索候補は雰囲気不一致。音はBlender対象外 | audio 1 | ✓ |

合計: image 2 / audio 1 / motion 0 / stock 7 / 3D の実行 0
```

- 末尾の合計を予算（`$game-asset-tools` §1 と結果の `budget`）と比べる。超えるなら identity の行を残し、functional を素材か描画に落とす。
- 前のターンの素材（`list_assets`）で済む行は経路を「既存」にする（作り直さない）。
- 2 回目以降は、変わった行だけ直す。

## 5. 絵柄をそろえる

1. 生成の指示には毎回 style-guide の 5 行と、その素材に関係する詳細基準を入れる。背景・キャラクターなどには「文字・ロゴを描かない」を添える。独立したタイトルロゴの生成は `$game-listing` references/title-logo.md に従い、確定したタイトルだけを描かせる。
2. 主役の絵は `hero.png` を元に作る（同じ特徴・同じ配色・同じ比率を指示に書き直す。「前と同じ」だけに頼らない）。
   画像そのものを参照に渡すときは、登録済みの設定画やコンセプトの素材に `edit_image` を使う（`generate_image` は参照画像を受け取らない）。
3. 連番は 1 枚ずつ作らず、1 回で 1 列を作って大きさと足元の位置をそろえる（`$game-asset-tools` §3.1）。
4. 素材はパック 1 つにそろえる。混ぜるなら色・形・比率・輪郭・描き込み・質感・陰影・視点を比較し、`asset-manifest.md` の理由に **採用 / 加工して採用 / 置換** を書く。色替えだけで合格にしない（references §3）。
5. マップの素材は変換表に合わせる: 形と描き込みが合うパックを選び、色は `look.gd recolor` でコンセプトへ寄せる。パックで形が合わなければ、コンセプトの画風で模様と縁を生成して `tiles.gd compose` でタイルにする（references/concept-to-map.md §3）。
6. 透過は結果の画像の透明部分を確かめる（市松模様が描かれた画像は透過ではない）。

## 6. 素材を増やす前に描画の基準を作る

- greybox の核ができたら、主役・床や壁・代表的な小物・光・HUD を同じ場面に置く。**代表場面を作ってから素材を量産する**。
  3D は材質と照明、2D はピクセルの粒度・輪郭・焼き込んだ影を基準に合わせる。
- 表現の数値は既存の tuning の配置に従い一か所で管理する。シーン間の違いは作品の意図を持つ変化にする。
- 2D の照明と色調は references §4 と `$game-godot`、3D の光・影・露出は references §5 と `$game-3d-and-bundles` に従う。
- ホラーなら暗い領域と局所的な光で不安を作り、必要な手掛かりが見えるようにする。昼間のホラーなど利用者の意図がある場合はそれに従う。
  「ホラー = 全部黒」「主役が見えない = 全体を明るくする」という一律の処理をしない。

### 6.1 スタート画面も作品の美術に含める

スタート画面を作る/変更する時は、主役/代表的な場所/盤面とメニューの余白を一緒に決める。
`design/style-guide.md`に、主役となる対象・縦横の構図・タイトルとメニューの文字の役割・本編と共通の形/材質を短く記録する。
作品に合う構図を選び、中央カード/ネオン/大きなロゴ等を全作品に同じ形で適用しない。
既存素材/承認済みの方向を再利用し、メニューのためだけに無関係な絵や有料素材を増やさない。
タイトルの装飾と操作ラベルを分け、生成背景/ボタン画像に文字を焼き込まない。
タイトルロゴは `$game-listing` references/title-logo.md の独立した透過素材を使い、アイコンと共用する。
主役の顔や特徴をメニューで隠さず、明るい背景部分でもラベルが読めるようにする。
構図/サイズは `$game-screen-layout` §5、機能/状態は `$game-ux` references/start-screen.md が正本。
細部の改善で新しいコンセプト承認を追加せず、方向変更がある場合だけ既存の§2を使う。

## 7. 実画面を見て修正する

`$game-playtest` の画像とプレビューを使い、references §6 の項目を `design/playtest.md` へ加える。
雰囲気・素材の統一感・明暗・手掛かり・HUD を**実画面と style-guide を比較して**判断する。
マップのある場面は、コンセプトと同じ視点・時間帯で撮った画像を `look.gd compare` でコンセプトと並べ、差を局所的に直す（references/concept-to-map.md §5）。
問題があれば場所・原因・修正を記録して直す。確認できた画面だけ ✓ にし、画像が無い版や見えない場面は未確認と書く。
コードや平均輝度だけで「世界観を確認済み」にしない。通常の試遊は最小限、thorough は利用者の明示依頼時だけという規則を守る。
