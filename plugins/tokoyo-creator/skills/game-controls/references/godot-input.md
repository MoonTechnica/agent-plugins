# Godot の入力（移動スティック・ボタン・InputMap・操作方法の画面）

Godot（新規・継続制作の既定）で操作を作る/直すときに読む。SKILL.md §2 の決まりごと（PC とスマホの両方・
48px 以上・同時押し 2 つまで・端からのスワイプ禁止など）はそのまま守る。§1〜§3 の JS 入力キット
（`assets/input.ts`・`createInput`）は旧 JS 作品のためのもので、Godot では下の部品に置き換える。
ジャンル別の割り当て（references/genres.md の表）は、キーの組み合わせとスマホの配置の目安として読む。

## 1. 移動はスターターの `tokoyo_touch_stick.gd` を使う（自作しない）

スマホで「動かし続ける」ゲームの移動は、`sample-godot`（対戦は `sample-godot-multiplayer`）にある
**`res://tokoyo_touch_stick.gd`** を使う。移動スティックを毎回自作すると、次の失敗が必ずどれか起きる:

| よくある失敗 | 体感 | 部品の挙動 |
|---|---|---|
| 固定位置のスティックで、触った所と中心がずれる | 触れた瞬間に勝手に走り出す / 端を触ると反応しない | **触れた所が中心**（左下の広い範囲のどこからでも始まる）。触れた瞬間は動かない |
| 遊び（dead zone）が無い / 大きすぎる | 止まりたいのに滑る / 少し倒しても動かない | 半径の 15% まで無反応、その外は 0 から連続して増える |
| スティックで遊びを付けた値を `Input.action_press(strength)` で流し、`Input.get_vector()` でもう一度 dead zone を掛ける / 移動を `ui_*`（既定 dead zone 0.5）で読む | 半分まで倒さないと動かず、急に速くなる | `get_move()` はスティックの値をそのまま返し（dead zone は 1 か所だけ）、キー/パッドは dead zone 0.2 を明示して読む |
| 指が縁を越えると止まる・戻すのに縁まで戻る | 切り返しが遅い | 縁を越えると**土台が指に付いてくる**ので、逆へ動かすとすぐ逆へ進む |
| 2 本目の指（ジャンプ）でスティックが飛ぶ | 跳ぶたびに移動が乱れる | **最初に触れた指だけ**を追う |
| 指を離さずに通知・ポーズ・画面外へ | 押しっぱなしで走り続ける | 離す・非表示・フォーカス喪失で必ず 0 に戻る |
| スティックがどこにあるか分からない | 最初に迷う | 止まっている間も左下に薄く表示（キー/パッドを使うと消え、画面に触れると出る） |

```gdscript
const TouchStick := preload("res://tokoyo_touch_stick.gd")
var stick: Control

func _ready() -> void:
	var hud := CanvasLayer.new()
	add_child(hud)
	stick = TouchStick.new()
	hud.add_child(stick)
	get_viewport().size_changed.connect(_layout)
	_layout()

func _layout() -> void:
	stick.set_safe_rect(_hud_safe_rect())   # starter の _host_safe_rect と同じ矩形（HUD 用のセーフエリア）

func _physics_process(delta: float) -> void:
	var move: Vector2 = stick.get_move(&"move_left", &"move_right", &"move_up", &"move_down")
	velocity = Vector2(move.x, move.y) * tuning.speed       # 3D は Vector3(move.x, 0, move.y) をカメラの向きで回す
	move_and_slide()
```

- 調整値（`@export`）: `radius`（既定 88。720 基準の論理 px）、`dead_zone`（0.15）、`directions`（0 = アナログ /
  4 / 8 = マス目やメニューのように方向を固定）、`follow`（true）、`zone`（セーフエリアに対する左下の始動範囲。
  既定は左半分・上 30% を除く）、`idle_alpha`（0.35）。変えるなら `tuning` と同じく 1 か所で決め、実機で確かめる。
- **始動範囲に別のボタンを置かない**（ポーズ・メニューは右上か上端、アクションボタンは右下）。スティックは UI より先に
  タッチを受け取るので、範囲の中のボタンは押せなくなる。
- 移動は自作のアクションで読む（`ui_left` などの `ui_*` は既定の dead zone が 0.5 で、メニュー用）。
- タイトル・ポーズ・会話・リザルトでは `stick.set_shown(false)`、プレイに戻るとき `true`。Host の一時停止
  （`TokoyoApp.is_paused()`）とシーン切替でも `reset()` を呼ぶ。
- 横スクロールで左右だけ使うなら `move.y` を捨てる（上キー/上入力をジャンプにしない）。上下に意味が無い
  ゲームで y を使うと、斜めに倒したときに遅く感じる → `move.x` を `sign(move.x) * minf(1, absf(move.x) * 1.3)` のように
  左右だけで最大に届くようにしてよい（`tuning` に置く）。
- キャラの向きは「最後に 0 でなかった move」の向き（止まっても向きを戻さない）。
- 3D はカメラの水平の向きで `move` を回してから使う（スティックの上 = 画面の奥）。

## 2. アクションボタンは `TouchScreenButton`（`Button` は使わない）

右下のジャンプ・攻撃などは **`TouchScreenButton`**（Node2D。CanvasLayer の下に置く）にし、`action` に
InputMap のアクション名を入れる。`visibility_mode = TouchScreenButton.VISIBILITY_TOUCHSCREEN_ONLY` で
タッチの無い端末では出ない。`texture_normal` / `texture_pressed` を必ず用意する（押している間の見た目が変わる）。
ゲームは `Input.is_action_just_pressed(&"jump")` を読むだけで、キー・パッド・画面のボタンが同じになる。

- **`Button` などの Control を画面のアクションボタンにしない**: タッチから作られるマウスのまねは
  1 本目の指だけなので、スティックを押さえたまま 2 本目の指で押しても反応しないことがある。
  メニュー（タイトル・ポーズ・設定・操作方法）は `Button` でよい（1 本指で操作するため）。
- 大きさは主ボタンが直径 120〜150（720 基準）、副ボタンは 96〜120。親指の弧に沿って主ボタンを一番外側・下に。
  `shape`（CircleShape2D）は見た目より一回り大きくし、`passby_press = true` で指を滑らせて押せるようにする
  （リズム・格闘のように押し分けが重要なら false）。
- ボタンの絵には動作のアイコンか 2〜4 文字（「ジャンプ」）を描く。キー名や A/B は描かない。

## 3. InputMap とイベント処理

- アクションは `project.godot` の `[input]` に定義し、**キー（物理キー `physical_keycode`）と
  ゲームパッドを同じアクションに登録**する。移動は WASD と矢印の両方、決定は Space/Enter とパッド下、
  戻るは Escape とパッド右、ポーズは Escape/P とパッドの Start。各アクションの `deadzone` は 0.2（新しく作るアクションの既定）のままにする。
- 遊びの入力は **`_unhandled_input`** か `Input.is_action_*`（`_physics_process` 内）で読む。HUD の Control は
  `mouse_filter = MOUSE_FILTER_IGNORE`（ボタン以外）にして、見えない Control が画面のタッチを食べないようにする。
- タッチとマウスを両方数える処理は、`InputEventMouseButton.device == InputEvent.DEVICE_ID_EMULATION` を除外する
  （まねのマウスと本物のタッチを二重に数えない）。
- 押しっぱなしは pause・会話・シーン切替・フォーカス喪失で解除する（`Input.action_release` / `stick.reset()`）。
- 入力方法の切り替え（最後に触った入力で説明を変える）は、`_input` で `InputEventScreenTouch` /
  `InputEventKey` / `InputEventJoypadButton` を見て 1 つの `input_mode` 変数に入れ、変わったときだけ説明を描き直す。
- ゲームパッドの機種名は `Input.get_joy_name(device)` から推定し（"PS" / "DualSense" / "Xbox" / "Nintendo" /
  "Switch" を含むか）、分からなければ「下のボタン」のように位置で書く。

## 4. 操作方法はメニューの専用画面で丁寧に説明する

操作の説明を**タイトル画面に並べない**。タイトルは主役の絵・ロゴ・「はじめる/つづきから」が主役で、
説明文があると開始を邪魔し、しかも誰も読まない。説明は次の 2 つに分ける。

1. **遊びの中で、その瞬間に一言**（`$game-ux` §1 の「最初の 1 手」）。最初の移動・最初のジャンプ・新しい仕掛けが
   初めて出たときに、該当する入力を 1 つだけ示す（「◀ ▶ で移動」「ジャンプボタンで跳ぶ」）。できたら消す。
2. **「操作方法」画面**: タイトルメニューの補助項目（「はじめる」の下の「操作方法」）と、ポーズメニューの項目から
   開く。開いても遊びは始まらず、閉じると元のメニューの同じ項目へ戻る。初回に読むことを強制しない。

「操作方法」画面に入れるもの:

| 区画 | 中身 |
|---|---|
| 入力方法の切り替え | 「タッチ」「キーボード・マウス」「コントローラー」のタブ。**今使っている入力のタブを開いた状態**で出す（ほかのタブも見られる） |
| 操作の一覧 | 行ごとに「入力の絵（キーの形・ボタンの丸・スティックの絵）」+「動作」+「ゲームの中で何が起きるか」。例: 「Space / ジャンプボタン ─ 跳ぶ。長押しで高く跳ぶ」 |
| タッチの配置図 | タッチのタブでは、画面の縮図に移動スティックとボタンの位置を描く（「左下のどこに触れても移動」） |
| 応用の操作 | ため・連続入力・回避の受付など、遊びを深くする操作。基本の行と分け、必要なゲームだけ |
| 遊び方（任意） | 目的と勝ち負けを 2〜4 行。コツが要るゲームは図 1 枚と 1 行。長い物語・設定は書かない |

- 文字は本文 16px 以上（720 基準で 28 以上を目安に実機で確認）、1 行 40 文字まで。画面に入り切らなければ
  スクロールさせ、スティック/矢印/パッドでも動かせるようにする。
- 実装中のアクションと一致させる（存在しない操作を書かない。InputMap と画面のボタンから作る）。
  操作を変えたターンはこの画面も直す。
- 閉じる: 「もどる」ボタン（44px 以上）・Escape・パッドの右ボタン。
- 1 画面で終わるゲーム（ワンボタン・タップだけのパズル）でも項目は置く。中身が 1〜2 行になってよい。

## 5. 確かめること（操作を作った/変えたターン）

- [ ] スマホ幅の縦・横で、移動スティックが左下のどこからでも始まり、触れた瞬間に動かず、縁で最大、離すと止まる
- [ ] スティックを押さえたまま右のボタンを押せる（2 本指）。ポーズ・会話の後に押しっぱなしが残らない
- [ ] キーボードとゲームパッドで同じアクションが動き、ゆっくり倒したスティックでもゆっくり動く
- [ ] タイトルとポーズから「操作方法」を開け、今の入力方法のタブが開き、閉じると元の項目に戻る
- [ ] 最初の 1 手の案内がプレイ中に出て、操作したら消える

ヘッドレスの実行ではタッチの当たり・指の届きやすさは分からない。実機/プレビューで触って確かめたことと、
未確認を分けて記録する。
