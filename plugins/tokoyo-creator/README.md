# TOKOYO Developer Kit

Build [TOKOYO.games](https://tokoyo.games) mini-games with the coding agent you already use on your own machine
(Claude Code, Codex, and others).

The Kit gives your agent the same Skills, instructions, and SDK that the TOKOYO.games generation agent uses,
plus a connection to the Platform (an MCP server called `tokoyo`). With them your agent can create a game,
pull it down, edit it locally, generate assets, and send it back to the Platform.

> This repository is generated by CI from the main TOKOYO.games repository. **Do not edit it directly** —
> your changes will be overwritten by the next generation.

## How it works

```text
 You (describe the game)
   │
   ▼
 Coding agent  ──  Kit Skills + SDK  ──▶  edits ./source/ on your machine
   │
   ├── Platform MCP (`tokoyo`) ◀──▶ TOKOYO.games   create / pull / push / assets / remix / proposals
   │
   ▼
 Push  ──▶  Platform validates it  ──▶  a draft appears in the editor (a URL is shown)
                                         └── you play-test, publish, and post from the browser
```

Things to know up front:

- **There is no local dev server.** Your agent builds and checks the game locally, but you play it
  in the editor in your browser after pushing. Each push becomes a new draft version.
- **Publishing and posting are done by you, in the browser.** The agent can create, edit, and push drafts,
  but it cannot make a game public.
- **Pushing runs the Platform's validation every time**, including a dynamic play check that only runs on the Platform.
  The Kit also runs the same static checks locally before each push, so most problems are caught early.

## Requirements

- Node.js 20 or later
- `git` 2.38 or later and [Git LFS](https://git-lfs.com) (`source/` is a git repository; images, sounds and 3D models are stored with LFS)
- `tar` (built in on macOS and Linux; Windows 10 and later ships `tar.exe`)
- A registered TOKOYO.games account (an anonymous guest account is not enough). You sign in through the browser the first time.
- Godot **4.5.1 stable** and its Web export templates, installed before building. Put the executable on `PATH`,
  or set `GODOT_BIN` to its absolute path. SDK `setup` installs npm dependencies, not the Godot toolchain.
- Network access: the Kit runs `npm ci` for the fixed SDK and server physics dependencies.

New games start from `sample-godot/`: GDScript and Godot scenes provide the same game source for Web and native.
For online games, use the shared `sample-godot-multiplayer/` contract and the existing Space Server.
JavaScript, Phaser and Babylon rendering templates are no longer provided.

## Quick start (Claude Code)

### 1. Install

```text
/plugin marketplace add MoonTechnica/agent-plugins
/plugin install tokoyo-creator@moon-technica
```

### 2. Sign in

Run `/mcp`, select `plugin:tokoyo-creator:tokoyo`, and approve the login in your browser.
You only need to do this once.

### 3. Make a game

Create a working folder and start Claude Code in it, then:

```text
/tokoyo-creator:new A jump game where you collect stars
```

The agent creates the game on the Platform, sets up your working directory, writes the code in `source/`,
and checks it. Then push it:

```text
/tokoyo-creator:push Added instructions screen
```

When the push succeeds, the editor opens in your browser (the agent also prints the URL). Play-test your draft there.
To keep working, tell the agent what to change, then push again.

### Commands

| Command | What it does |
|---|---|
| `/tokoyo-creator:new <idea>` | Start a new game: creates it on the Platform and sets up a working directory. |
| `/tokoyo-creator:pull <app_id or editor URL>` | Bring the latest version of an existing game to your machine (to continue work, or after you edited it in the browser). |
| `/tokoyo-creator:check` | Run the pre-push checks locally (the Platform's importer and static validation). |
| `/tokoyo-creator:push <message>` | Check, then send your game to the Platform as a new draft. The message becomes the version note. |
| `/tokoyo-creator:remix <game page URL>` | Remix (fork) a game someone published and start working on your copy. |
| `/tokoyo-creator:propose <title>` | Propose your remix's changes back to the original game, like a GitHub pull request. |
| `/tokoyo-creator:proposals` | Review proposals other people sent to your game, then comment, merge, or decline. |

You can also just describe what you want in plain language ("push this", "make the enemies faster") — the agent picks the right Skill.

Opening, withdrawing, commenting on, and merging a proposal all reach another person, so Claude Code
asks you to confirm each one every time (allow rules cannot skip this).

### Update

```text
/plugin marketplace update moon-technica
```

## Quick start (Codex)

### 1. Install

```text
codex plugin marketplace add MoonTechnica/agent-plugins
codex plugin add tokoyo-creator@moon-technica
codex mcp login tokoyo
```

Then start a new Codex session. (You can also install from `/plugins` inside Codex.)

### 2. Use it

In Codex, call the Skills with `$`:

| Skill | What it does |
|---|---|
| `$tokoyo-new` | Start a new game. |
| `$tokoyo-pull` | Bring an existing game's latest version to your machine. |
| `$tokoyo-push` | Check and send your game to the Platform. |
| `$tokoyo-remix` | Remix a published game. |
| `$tokoyo-propose` | Propose your remix's changes to the original. |
| `$tokoyo-proposals` | Review proposals sent to your game. |

Or just describe what you want ("create a new TOKOYO.games game: a one-button runner").

### 3. Require approval for proposal actions

Opening, withdrawing, commenting on, and merging a proposal reach other people, so make them approval-only.
Codex plugins cannot ship this setting, so add the following to `~/.codex/config.toml`
(`node <kit>/scripts/kit.mjs codex-config` prints the same text):

```toml
[plugins."tokoyo-creator@moon-technica".mcp_servers.tokoyo]
default_tools_approval_mode = "writes"

[plugins."tokoyo-creator@moon-technica".mcp_servers.tokoyo.tools.open_proposal]
approval_mode = "approve"

[plugins."tokoyo-creator@moon-technica".mcp_servers.tokoyo.tools.close_proposal]
approval_mode = "approve"

[plugins."tokoyo-creator@moon-technica".mcp_servers.tokoyo.tools.comment_proposal]
approval_mode = "approve"

[plugins."tokoyo-creator@moon-technica".mcp_servers.tokoyo.tools.merge_proposal]
approval_mode = "approve"
```

### Update

```text
codex plugin marketplace upgrade moon-technica
```

### About the pre-push hook

The Kit ships a hook that runs the checks before every push. In Codex it stays off until you trust it in `/hooks`.
If you do not trust it, `$tokoyo-push` still runs the checks as one of its steps.

## Other agents

Any agent that supports Skills and remote MCP servers can use the Kit.

1. **Get the Kit.**
   ```bash
   git clone https://github.com/MoonTechnica/agent-plugins ~/tokoyo-creator-kit
   ```
   The Kit root is `~/tokoyo-creator-kit/plugins/tokoyo-creator`.
2. **Install the Skills.** Link `plugins/tokoyo-creator/skills/*` into your agent's Skills folder
   (for example `.agents/skills/`). If you only want the knowledge, `npx skills add MoonTechnica/agent-plugins`
   also works — but pushing needs the clone from step 1, and the Skill will ask you where it is.
3. **Register the MCP server.** Transport: Streamable HTTP with OAuth. URL: `https://tokoyo.games/mcp/creator`.
   If your client lets you pin the OAuth callback port, use `43125`.
4. **Sign in** from your agent's MCP screen.

## What happens in your working directory

`/tokoyo-creator:new` (or `pull`) creates a folder like this:

| Path | What it is |
|---|---|
| `.tokoyo.json` | Links the folder to a game on the Platform (app id, session id, the branch you push, the commit you last pulled, the Kit location). Do not edit by hand. |
| `source/` | **Your game's project — a git repository.** This is where you and the agent work and commit. |
| `input/` | The Platform's play-test of the version you pulled. |
| `assets-cache/` | Assets downloaded from the asset tools; copy what you need into `source/`. |
| `outputs/` | The three files that get sent: `source.bundle` (your new commits), `dist.tar.gz`, and `build-report.json`. Generated by `pack`. |
| `AGENTS.md` | Short guidance for the agent working in this folder. |

## Typical workflows

**Make a new game** — `new` → describe and iterate → `push` → open the editor URL, play-test, publish.

**Keep working on a game** — `pull <app_id>` → ask for changes → `push`. If you also edited the game in the browser,
pull first so you start from the newest version. If the Platform moved on while you were working,
the agent rebases your commits onto it (like `git pull --rebase`) and resolves any conflicts.

**Add art and sound** — Ask for it in plain language. The agent first looks for free CC0 assets
(Kenney, Quaternius) and imports them, and generates images, sound effects, music, and 3D models
only for what is missing. Generated assets use the game's asset budget (per game, per UTC day).

**Contribute to someone else's game** — `remix <game page URL>` → make one focused change → `push`
→ wait until it is validated (no need to publish) → `propose`. The owner reviews it and can merge it
into their game's draft. Keep each proposal to a single purpose; unrelated edits make it harder to review.

**Review proposals sent to your game** — `proposals`. The proposed commit arrives with `pull` (as
`refs/remotes/tokoyo/proposals/<id>`); the agent reads it with `git diff` and summarizes what changes and what could conflict.
Merging puts the result into your draft; it does not publish it.

## Command-line tool (advanced)

The Skills drive these for you, but you can run them yourself from the working directory:

```bash
node <kit>/scripts/kit.mjs <command> [--flag value]
```

| Command | What it does |
|---|---|
| `setup` | Unpack the SDK and install its dependencies (`npm ci`). Safe to repeat. |
| `clone` | Create a working directory for a game: `source/` becomes a git repository of its history. |
| `pull` | Fetch the Platform's new commits and rebase your branch onto them. |
| `login` | Sign in for Git LFS (images, sounds, 3D). Opens the browser once; the token stays in `~/.config/tokoyo/`. |
| `build` | Build `source/dist/` (runs the game's `build.mjs`, or the default steps). The only way to build. |
| `pack` | Bundle your new commits as `outputs/source.bundle`, pack `outputs/dist.tar.gz`, and print the push arguments. |
| `check` | Run the Platform's importer and static validation locally. |
| `upload` | Upload the LFS files, then the packed files to the signed URLs from `begin_build`. |
| `assets add` | Put an asset from the game's asset library under `source/`. |
| `open` | Open the editor URL in your browser. |
| `link` | Re-point `source/`, its git settings and `.tokoyo.json` at a newer Kit (after updating). |
| `codex-config` | Print the recommended Codex approval settings. |

## Continue between local and cloud

Use the `tokoyo-continue` Skill with the handoff ID from the editor. The equivalent CLI is
`node <kit>/scripts/kit.mjs continue --handoff-id <id> --directory <new-empty-directory>`.
It verifies the pinned source, LFS objects, SDK and shared context, accepts the handoff, and checks
that the writer is still current before enabling edits. Retry the same command after a connection
failure. Existing unrelated files are never overwritten.

To receive editor requests, keep `node <kit>/scripts/kit.mjs connect --workspace <dedicated-root> --agent codex`
(or `claude`) running in a terminal, then approve its displayed challenge in the editor. This receives
work without starting an agent. Add `--allow-agent-run` explicitly to allow dedicated agent children.
Automatic execution requires macOS, Codex CLI 0.164.0 (or Claude Code 2.1.309 with that sandbox helper),
and a dedicated workspace outside ancestor `.codex/config.toml` configuration. Other environments
stay in receive-only mode. No parent OAuth token is passed to the child. Ctrl-C stops the connector and
its own active child; `disconnect --workspace <dedicated-root>` revokes the registration.

Save a structured shared memo to `outputs/handoff-context.json`, commit changes in `source/`, then run
`checkpoint --context-file outputs/handoff-context.json` before preparing a return to the cloud.
In connector-managed workspaces, use the editor to switch; its parent connector performs the checkpoint with the active command identity. The memo carries decisions, attempts, next steps and checks; full provider conversations are not migrated.
Pinned SDKs and Kit files are copied to a private hash-keyed snapshot under each workspace, so receiving
a different release cannot replace another workspace's SDK. The child can write source/ and outputs/
while metadata, the snapshot and parent credentials remain protected. Buildable results are built and
validated by the parent; failed builds retain a source checkpoint and do not claim a new playable preview.
Managed workspaces use configuration schema 2 and require Kit revision 9 or newer. Do not edit their
execution identity by hand. A changed writer or failed checkpoint leaves local changes available for recovery.

## Troubleshooting

| Symptom | What to do |
|---|---|
| "Kit is outdated" / `SDK_VERSION_DEPRECATED` when pushing | Update the Kit (see the Update sections above), then ask the agent to set up the SDK again. |
| The push fails validation | Ask the agent to read the validation report and fix the problem. Running `check` locally reproduces most failures. |
| "Someone changed the game first" / `STALE_BASE` | The game moved on (for example, you edited it in the browser). The agent pulls, rebases your commits, and pushes again. |
| LFS asks for credentials / `LFS_OBJECT_MISSING` | Run `node <kit>/scripts/kit.mjs login` once, then push again. |
| `author_mismatch` | A commit is not in your name. Do not change `user.name` / `user.email` in `source/`; the agent resets the author and pushes again. |
| Rate or quota limit | Wait a bit and try again. Do not resend repeatedly. Asset budgets reset daily (UTC). |
| Permission error on a game | You can only edit games owned by your account or a team you belong to. |
| `/mcp` shows the server as not signed in | Sign in again from `/mcp` (Claude Code) or run `codex mcp login tokoyo` (Codex). |

## Connecting to a different Platform environment

In Claude Code, set the `GAME_SNS_MCP_URL` environment variable to point the MCP server somewhere else
(for example, local development: `http://localhost:4042/mcp/creator`).
